第 7 章 · 项目二：图片书签社交网站

追踪用户行为

社交网站的灵魂是“人与人的关系”。这一章给用户加上关注功能，并做一个“动态流”： 你关注的人收藏了什么图片、给什么点了赞、又关注了谁。途中会学到带中间模型的多对多、泛型关系、 查询优化、信号，以及用 Redis 做高速计数和排行榜。

本章目标

  • 用 through= 中间模型实现“关注”这种自引用、非对称的多对多关系
  • 用 contenttypes 框架和 GenericForeignKey 让一条动态指向任意模型
  • 掌握 select_related() 与 prefetch_related() 的区别
  • 用信号维护冗余计数，理解 AppConfig.ready()
  • 用 Django Debug Toolbar 查看 SQL、模板、信号
  • 用 Redis 的 INCR 和有序集合实现浏览计数与排行

关注系统：带中间模型的多对多

“A 关注 B”是用户与用户之间的多对多关系，而且我们还想记录“什么时候关注的”。需要额外字段时，就自己定义中间模型：

class Contact(models.Model):
    user_from = models.ForeignKey(settings.AUTH_USER_MODEL, related_name='rel_from_set',
                                  on_delete=models.CASCADE)      # 发起关注的人
    user_to = models.ForeignKey(settings.AUTH_USER_MODEL, related_name='rel_to_set',
                                on_delete=models.CASCADE)        # 被关注的人
    created = models.DateTimeField(auto_now_add=True)

    class Meta:
        indexes = [models.Index(fields=['-created'])]
        ordering = ['-created']

    def __str__(self):
        return f'{self.user_from} follows {self.user_to}'


# 书中的做法：给内置 User 动态加一个字段（猴子补丁）

动态流与泛型关系

一条动态可能是“alice 收藏了图片 X”，也可能是“alice 关注了用户 bob”。目标对象的类型不固定，普通外键做不到 —— 这就要用 contenttypes 框架。

from django.contrib.contenttypes.fields import GenericForeignKey
from django.contrib.contenttypes.models import ContentType


class Action(models.Model):
    user = models.ForeignKey(settings.AUTH_USER_MODEL, related_name='actions', on_delete=models.CASCADE)
    verb = models.CharField(max_length=255)
    created = models.DateTimeField(auto_now_add=True)
    target_ct = models.ForeignKey(ContentType, blank=True, null=True,
                                  related_name='target_obj', on_delete=models.CASCADE)
    target_id = models.PositiveIntegerField(null=True, blank=True)
    target = GenericForeignKey('target_ct', 'target_id')

    class Meta:
        indexes = [
            models.Index(fields=['-created']),
            models.Index(fields=['target_ct', 'target_id']),     # 按目标查动态时用
        ]
        ordering = ['-created']

创建动态：一个带去重的小工具函数

import datetime

from django.contrib.contenttypes.models import ContentType
from django.utils import timezone

from .models import Action


def create_action(user, verb, target=None):
    # 一分钟内相同的动作不重复记录（防止用户狂点“赞/取消赞”刷屏）
    last_minute = timezone.now() - datetime.timedelta(seconds=60)
    similar_actions = Action.objects.filter(user_id=user.id, verb=verb, created__gte=last_minute)
    if target:
        target_ct = ContentType.objects.get_for_model(target)
        similar_actions = similar_actions.filter(target_ct=target_ct, target_id=target.id)
    if not similar_actions:
        Action(user=user, verb=verb, target=target).save()
        return True
    return False

然后在四个地方调用：收藏图片 'bookmarked image'、点赞 'likes'、注册 'has created an account'、关注 'is following'。

信号：维护冗余计数

“按点赞数排序”用 annotate(Count('users_like')) 每次都要 JOIN + GROUP BY。 如果把点赞数冗余存到 Image.total_likes 字段，排序就只是一个普通的索引扫描。代价是：必须保证它始终正确。 

from django.db.models.signals import m2m_changed
from django.dispatch import receiver

from .models import Image


@receiver(m2m_changed, sender=Image.users_like.through)
def users_like_changed(sender, instance, **kwargs):
    instance.total_likes = instance.users_like.count()
    instance.save()


class ImagesConfig(AppConfig):
    default_auto_field = 'django.db.models.BigAutoField'
    name = 'images'

    def ready(self):
        import images.signals       # 在应用加载完成后导入，注册接收函数
常用模型信号何时发送
pre_save / post_save模型 save() 前 / 后（post_save 有 created 参数）
pre_delete / post_delete删除前 / 后（包括 QuerySet 批量删除）
m2m_changed多对多关系变化，action 参数区分 pre/post_add、remove、clear
⚠ update()、bulk_create() 不会触发 save 信号

批量操作绕过了模型的 save()，所以 pre_save/post_save 不会发送。依赖信号维护的冗余数据在这些场景下会失真 —— 这是“慎用信号”的另一个原因。

用 Redis 计数和排行

每次打开图片详情页都 UPDATE 一次数据库来计数，代价不小。Redis 是内存中的键值数据库， 支持字符串、哈希、列表、集合、有序集合等结构，做计数器和排行榜正合适。

import redis
from django.conf import settings

r = redis.Redis(host=settings.REDIS_HOST, port=settings.REDIS_PORT, db=settings.REDIS_DB)


def image_detail(request, id, slug):
    image = get_object_or_404(Image, id=id, slug=slug)
    total_views = r.incr(f'image:{image.id}:views')
    r.zincrby('image_ranking', 1, image.id)
    return render(request, 'images/image/detail.html',
                  {'section': 'images', 'image': image, 'total_views': total_views})


@login_required
def image_ranking(request):
    image_ranking = r.zrange('image_ranking', 0, -1, desc=True)[:10]
    image_ranking_ids = [int(id) for id in image_ranking]
    most_viewed = list(Image.objects.filter(id__in=image_ranking_ids))
    most_viewed.sort(key=lambda x: image_ranking_ids.index(x.id))   # 按 Redis 给的顺序排
    return render(request, 'images/image/ranking.html', {'section': 'images', 'most_viewed': most_viewed})

书里自己也承认“这不是推荐做法”。它依赖模块导入顺序、对类型检查和 IDE 不可见、别的应用也可能往 User 上加同名属性。 如果第 4 章就用了自定义用户模型，这里只需要在模型里正常声明一个字段：

有问题 关注关系缺少数据库约束，还能关注自己

get_or_create 不是原子的，并发的两次点击可能插入两行相同的关注；视图也没阻止 user == request.user。用约束让数据库兜底（注意 Django 5.1 起 CheckConstraint 的参数名从 check 改为 condition）：

class Contact(models.Model):
    # ...
    class Meta:
        constraints = [
            models.UniqueConstraint(fields=['user_from', 'user_to'], name='unique_follow'),
            models.CheckConstraint(
                condition=~models.Q(user_from=models.F('user_to')), name='no_self_follow',
            ),
        ]

有问题 信号接收函数被多次调用，而且反向操作会崩 Chapter07/bookmarks/images/signals.py:7

m2m_changed 在一次 add() 中会发送 pre_add 和 post_add 两次，接收函数没有判断 action，于是每次点赞都 COUNT + 全字段 save() 两遍。 更严重的是：如果有人从另一端操作 user.images_liked.add(image)，信号的 instance 是 User，instance.users_like 不存在，直接抛异常。 另外 instance.save() 保存全部字段，可能覆盖别人刚改过的标题等数据。 

@receiver(m2m_changed, sender=Image.users_like.through)
def users_like_changed(sender, instance, action, reverse, pk_set, **kwargs):
    if action not in ('post_add', 'post_remove', 'post_clear'):
        return
    image_ids = pk_set if reverse else {instance.pk}       # reverse=True 时 instance 是 User
    for image_id in image_ids or ():
        Image.objects.filter(pk=image_id).update(
            total_likes=Image.users_like.through.objects.filter(image_id=image_id).count()
        )

TSD 对信号的态度是“最后才考虑的手段”：本例中点赞只在 image_like 一个地方发生，直接在视图（或一个 service 函数）里显式更新计数更清晰，也更好测试。

建议改进 target_id 的类型与主键不匹配 actions/models.py:22

项目的 DEFAULT_AUTO_FIELD 是 64 位的 BigAutoField，而 target_id 是 32 位的 PositiveIntegerField，主键超过 21 亿时就存不下。应改为 PositiveBigIntegerField。另外泛型外键没有数据库级引用完整性：图片删了，指向它的 Action 还在，模板里 action.target 变成 None —— 可以给 Image 加 GenericRelation(Action)，删除图片时会级联删除相关动态。

建议改进 Redis 连接与排行查询

① 在 views.py 模块顶层创建连接、写死主机端口，Redis 一挂图片详情页就 500。更好的做法是用 REDIS_URL 环境变量 + redis.from_url() 统一创建，或者直接用 Django 的缓存框架（第 14 章），并在计数失败时降级而不是报错。 ② zrange(…, 0, -1)[:10] 先把整个有序集合取回来再在 Python 里切片，应当让 Redis 只返回前 10 个：r.zrange('image_ranking', 0, 9, desc=True)。 ③ 图片被删后它的 ID 仍留在排行里，需要在删除时 ZREM。

建议改进 Debug Toolbar 无条件启用 bookmarks/settings.py:43

Debug Toolbar 被写进了唯一的 settings 和根 URL 配置，生产环境也会加载这个包（虽然它自己会检查 DEBUG）。按 TSD 的“多设置文件”做法，把它只放在 settings/local.py 里，URL 也用 if settings.DEBUG: 包起来（第 17 章会拆分设置）。

补充知识 小优化：exists() 与列表页 N+1

create_action 里 if not similar_actions: 会把查询结果全部取回，只需要判断有无时用 .exists()；dashboard 里 if following_ids: 也是如此。user_list 模板对每个用户访问 user.profile.photo，应加 select_related('profile') 并分页。

补充知识 仓库里的 AI 练习：用信号自动创建 Profile

Chapter07/prompts/task.md 让读者用信号在创建用户时自动创建 Profile。参考实现（写在 account/signals.py，并在 AccountConfig.ready() 中导入）：

from django.conf import settings
from django.db.models.signals import post_save
from django.dispatch import receiver

from .models import Profile


@receiver(post_save, sender=settings.AUTH_USER_MODEL)
def create_profile(sender, instance, created, **kwargs):
    if created:
        Profile.objects.get_or_create(user=instance)

这样就可以删掉 register 视图和社交登录 pipeline 里手动创建 Profile 的代码，第 4 章点评提到的“Admin 创建的用户没有 Profile”也随之解决。

小结

  • 多对多需要额外字段时，用 through= 指定中间模型；自引用的非对称关系要写 symmetrical=False。
  • contenttypes + GenericForeignKey 让一个字段指向任意模型，代价是失去数据库引用完整性。
  • select_related 用 JOIN 处理外键/一对一，prefetch_related 用额外查询处理多对多、反向和泛型关系。
  • 信号在 AppConfig.ready() 中注册，是同步执行的；批量操作不会触发 save 信号。
  • Redis 适合计数、排行、缓存、队列等高频数据。
