Spring Boot 版 · 第 1 章 · 项目一：博客

创建博客应用

和 Django 版第 1 章一样，我们从零搭一个能跑的博客：定义文章模型、建表、做一个管理后台， 再用控制器和模板把文章展示出来。区别在于，Django 用一个框架“全包”的事情， 在 Spring Boot 里由好几个项目分工完成 —— 这一章的重点就是认识它们各自的位置。

本章目标

  • 画出 Spring MVC 处理一个请求的路线，并和 Django 的 MTV 对上号
  • 看懂 pom.xml、入口类和 application.yaml，知道它们分别对应 Django 的什么
  • 用 JPA 注解写出 Post 实体：字段、枚举、外键、自动时间戳、索引
  • 用 Flyway 手写迁移脚本，理解它和 makemigrations 最大的不同
  • 用 Spring Data 仓库完成 QuerySet 的常见操作，并用 @EntityGraph 避免 N+1
  • 写控制器和 Thymeleaf 模板，掌握布局继承、URL 生成和“过滤器”的替代方案
  • 理解为什么要手写后台，以及 Spring Security 在本章承担的最小职责

对应的 Django 讲解见 Django 版第 1 章；本章代码在 springboot/Chapter01/。

Spring MVC 是怎么处理请求的

Django 用 MTV 描述自己：URL 配置派发请求，视图协调，模型管数据，模板管外观。 Spring MVC 的角色几乎一一对应，只是名字不同，而且多了一个“总调度”：DispatcherServlet。

  1. 请求先进入内嵌的 Tomcat，穿过一串 Servlet 过滤器。Spring Security 就是其中之一，它负责登录状态、CSRF 校验等 —— 相当于 Django 的中间件。
  2. 过滤器放行后，请求交给 DispatcherServlet。它启动时已经扫描过所有带 @GetMapping 等注解的方法，建好了“URL → 方法”的映射表，相当于 Django 的 urls.py。
  3. DispatcherServlet 调用匹配到的控制器方法，并按参数上的注解自动准备好参数（路径变量、查询参数、当前用户……）。
  4. 控制器通过仓库读数据。仓库背后是 JPA/Hibernate，会把方法调用翻译成 SQL。
  5. 控制器把数据放进 Model，返回一个视图名（字符串，例如 "blog/post/detail"）。
  6. 视图解析器找到 templates/blog/post/detail.html，交给 Thymeleaf 渲染成 HTML 写回响应。

🔎 最大的不同：依赖注入容器

Django 的视图里直接 from .models import Post，想用什么就导入什么。 Spring 里，控制器、仓库、配置类都是容器管理的 Bean：控制器在构造器里声明“我需要一个 PostRepository”， 容器创建控制器时自动把仓库实例传进来。这就是依赖注入。 它的好处在测试时最明显：可以轻松把某个 Bean 替换成假的实现（第 2 章会把邮件发送器换成 Mock）。

实体：用 JPA 注解描述 Post

下面把 Django 的 Post 模型和 Spring 的实体放在一起比较。先看整体，再逐项拆开。

Django · blog/models.py
class Post(models.Model):
    class Status(models.TextChoices):
        DRAFT = 'DF', 'Draft'
        PUBLISHED = 'PB', 'Published'

    title = models.CharField(max_length=250)
    slug = models.SlugField(max_length=250)
    author = models.ForeignKey(
        settings.AUTH_USER_MODEL,

    body = models.TextField()

    created = models.DateTimeField(auto_now_add=True)
    updated = models.DateTimeField(auto_now=True)

Spring · blog/Post.java（去掉 getter/setter）
@Entity
@Table(name = "blog_post", indexes = @Index(
        name = "blog_post_publish_idx", columnList = "publish DESC"))
public class Post {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 250)
    private String title;

    @Column(nullable = false, length = 250)
    private String slug;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "author_id")
    private User author;

    @Column(nullable = false, columnDefinition = "text")
    private String body;

    @Column(nullable = false)
    private OffsetDateTime publish = OffsetDateTime.now(ZoneOffset.UTC);

    @CreationTimestamp
    @Column(nullable = false, updatable = false)
    private OffsetDateTime created;

    @UpdateTimestamp
    @Column(nullable = false)
    private OffsetDateTime updated;

    @Column(nullable = false, length = 2)
    private PostStatus status = PostStatus.DRAFT;

    protected Post() { }   // JPA 需要无参构造器

    @Override
    public String toString() { return title; }
}

枚举选项：TextChoices 与 enum + AttributeConverter

Django 的 TextChoices 同时定义了“数据库里存什么”（'DF'）和“界面上显示什么”（'Draft'）。 Java 的 enum 可以带字段，做到同样的事；再写一个 AttributeConverter 告诉 JPA 用代码值存库： 

public enum PostStatus {
    DRAFT("DF", "Draft"),
    PUBLISHED("PB", "Published");

    private final String code;
    private final String label;
    // 构造器、getter、fromCode(...) 略
}

@Converter(autoApply = true)          // 所有 PostStatus 类型的字段自动使用
public class PostStatusConverter implements AttributeConverter<PostStatus, String> {
    public String convertToDatabaseColumn(PostStatus status) {
        return status == null ? null : status.getCode();          // PUBLISHED → "PB"
    }
    public PostStatus convertToEntityAttribute(String code) {
        return code == null ? null : PostStatus.fromCode(code);   // "PB" → PUBLISHED
    }
}
⚠ 别用 @Enumerated(EnumType.ORDINAL)

JPA 默认把枚举存成序号（0、1），以后在中间插入一个新状态，已有数据的含义就全乱了。 最省事的安全写法是 @Enumerated(EnumType.STRING)（存 'DRAFT'）， 这里为了和 Django 的表结构保持一致才用了转换器。

外键为什么是 LAZY

@ManyToOne 默认是 EAGER：查文章时总会 JOIN 出作者，即使你用不到。 最佳实践是一律改成 FetchType.LAZY，需要作者时再在查询里显式声明“顺带取出来”。 这和 Django 的默认行为一致 —— Django 访问 post.author 时才发 SQL，需要预取时写 select_related。

迁移：Flyway 与 makemigrations

这是两个框架差异最大的地方之一。

-- blog/migrations/0001_initial.py
CREATE TABLE blog_post (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title      VARCHAR(250) NOT NULL,
    slug       VARCHAR(250) NOT NULL,
    author_id  BIGINT       NOT NULL REFERENCES auth_user (id) ON DELETE CASCADE,
    body       TEXT         NOT NULL,
    publish    TIMESTAMP WITH TIME ZONE NOT NULL,
    created    TIMESTAMP WITH TIME ZONE NOT NULL,
    updated    TIMESTAMP WITH TIME ZONE NOT NULL,
    status     VARCHAR(2)   NOT NULL DEFAULT 'DF'
);

-- Meta.indexes = [models.Index(fields=['-publish'])]
CREATE INDEX blog_post_publish_idx ON blog_post (publish DESC);
-- Django 会自动给外键和 SlugField 建索引，手写 SQL 时别忘了
CREATE INDEX blog_post_author_id_idx ON blog_post (author_id);
CREATE INDEX blog_post_slug_idx ON blog_post (slug);
Django 命令Spring 里怎么做
makemigrations新建 V<下一个版本号>__描述.sql，自己写 DDL
sqlmigrate blog 0001不需要 —— 脚本本身就是 SQL
migrate应用启动时 Flyway 自动执行未执行过的脚本（也可用 Flyway Maven 插件单独执行）
showmigrations查 flyway_schema_history 表，或开启 Actuator 的 /actuator/flyway
回滚到某个迁移Flyway 社区版不支持 undo，写一个新的“反向”脚本
⚠ 为什么不用 ddl-auto=update 让 Hibernate 自动建表

update 只会“加”，不会删列、改类型、迁移数据，也不留历史记录，在团队和生产环境里迟早出事。 正确分工是：表结构由 Flyway 脚本决定（可审查、可重放、进版本库），Hibernate 用 validate 在启动时核对实体和表是否一致。 手写 SQL 确实比 makemigrations 多花功夫，但你对每一列、每个索引都一清二楚。

仓库：Spring Data 对照 QuerySet

Django 用 Post.objects（Manager）作为查询入口。Spring Data 的做法是：你只声明一个接口， Spring 在运行时自动生成实现。继承 JpaRepository 就自带了 save、findById、findAll、delete、count 等方法。 

public interface PostRepository extends JpaRepository<Post, Long>, JpaSpecificationExecutor<Post> {

    // 方法名就是查询：WHERE status = ? ORDER BY publish DESC
    @EntityGraph(attributePaths = "author")      // 顺带 JOIN 出作者 ≈ select_related('author')
    List<Post> findByStatusOrderByPublishDesc(PostStatus status);

    @EntityGraph(attributePaths = "author")
    Optional<Post> findByIdAndStatus(Long id, PostStatus status);

    long countByStatus(PostStatus status);

    // 自定义管理器 Post.published 的替代品：接口里的 default 方法
    default List<Post> findPublished() {
        return findByStatusOrderByPublishDesc(PostStatus.PUBLISHED);
    }

    default Optional<Post> findPublishedById(Long id) {
        return findByIdAndStatus(id, PostStatus.PUBLISHED);
    }

    // 方法名表达不了的，就写 JPQL（面向实体的 SQL）
    @Query("""
            select p from FavouritePost f
              join f.post p
              join fetch p.author
            where f.user.id = :userId
            order by f.created desc
            """)
    List<Post> findFavouritesOf(@Param("userId") Long userId);
}

ⓘ 不同之处：仓库方法是“立即执行”的

Django 的 QuerySet 是惰性的，可以一路 .filter().exclude().order_by() 链下去，最后才发 SQL。 Spring Data 的仓库方法一调用就执行查询、返回结果集合。需要“动态拼条件”时用 Specification（第 1 章后台里就有）， 它才是 Q 对象和链式 filter 的对应物。

N+1 问题与 open-in-view

列表页要显示每篇文章的作者。如果查文章时没把作者一起取出来，模板里每访问一次 post.author 就会多一条 SQL —— 10 篇文章 11 条查询，这就是 N+1。Django 版原代码其实也有这个问题（没写 select_related）。

Spring Boot 默认开启 Open Session In View：数据库会话一直开到模板渲染结束，懒加载“总能成功”，N+1 就被悄悄掩盖了。 本项目在配置里把它关掉（spring.jpa.open-in-view: false），于是模板里再访问未加载的关联会直接抛 LazyInitializationException， 逼着我们在查询时用 @EntityGraph(attributePaths = "author") 把需要的数据取全。

Django
posts = Post.published.select_related('author')
Spring
@EntityGraph(attributePaths = "author")
List<Post> findByStatusOrderByPublishDesc(PostStatus status);

控制器与 URL

Django 把“视图函数”和“URL 规则”分在两个文件里；Spring 把 URL 直接写在方法上。

Django · blog/views.py + urls.py

                  'blog/post/list.html',
                  {'posts': posts})

def post_detail(request, id):
    post = get_object_or_404(
        Post, id=id,
        status=Post.Status.PUBLISHED)
    ...

# urls.py
app_name = 'blog'
urlpatterns = [
    path('', views.post_list, name='post_list'),
    path('<int:id>/', views.post_detail,
         name='post_detail'),

Spring · blog/BlogController.java
@Controller
@RequestMapping("/blog")
public class BlogController {

    private final PostRepository posts;
    // 构造器注入：容器自动传入仓库实例
    public BlogController(PostRepository posts, ...) {
        this.posts = posts;
    }

    @GetMapping({"", "/"})
    public String postList(Model model) {
        model.addAttribute("posts", posts.findPublished());
        return "blog/post/list";   // 视图名
    }

    @GetMapping("/{id}/")
    public String postDetail(@PathVariable Long id,
                             @AuthenticationPrincipal CurrentUser me,
                             Model model) {
        Post post = posts.findPublishedById(id)
            .orElseThrow(() -> new NotFoundException(
                "No Post matches the given query."));
        ...
        return "blog/post/detail";
    }
}
  • @RequestMapping("/blog") 加在类上 ≈ 主 urls.py 里的 path('blog/', include(...))。
  • {id} + @PathVariable Long id ≈ <int:id>：路径片段会被转换成 Long，转换失败返回 400。
  • Model ≈ 传给 render 的上下文字典；返回的字符串是模板路径（不带 .html）。
  • return "redirect:/blog/1/" ≈ HttpResponseRedirect / redirect()。

get_object_or_404 的替代品

仓库返回 Optional，找不到时抛一个带 @ResponseStatus(NOT_FOUND) 的异常，Spring 就会返回 404，并渲染 templates/error/404.html（相当于 Django 的 404.html）：

@ResponseStatus(HttpStatus.NOT_FOUND)
public class NotFoundException extends RuntimeException {
    public NotFoundException(String message) { super(message); }
}
⚠ 结尾斜杠：Spring 6 起不再自动匹配

Django 的 URL 习惯以 / 结尾，访问 /blog 时 APPEND_SLASH 会重定向到 /blog/。 Spring Framework 6 起，/blog/1 和 /blog/1/ 被视为不同的 URL。 本项目为了和 Django 版保持一致，映射里都显式写了结尾斜杠；列表页用 {"", "/"} 同时接受两种写法。

反向解析 URL

Django 用 {% url 'blog:post_detail' post.id %} 按名字生成链接，改 URL 规则时模板不用动。 Thymeleaf 的 @{...} 负责拼接上下文路径和参数，但 URL 模式本身要写出来：

Django 模板
<a href="{% url 'blog:post_detail' post.id %}">
<a href="{{ post.get_absolute_url }}">
Thymeleaf 模板
<a th:href="@{/blog/{id}/(id=${post.id})}">
<a th:href="@{${post.absoluteUrl}}">

为了减少重复，实体上也保留了一个 getAbsoluteUrl() 方法（和 Django 的 get_absolute_url 同名同义）， 模板里写 ${post.absoluteUrl} 就会调用它。Spring 也有按“映射名”反向生成 URL 的机制（MvcUriComponentsBuilder，模板里是 #mvc.url('BC#postDetail')）， 但生成的是带主机名的绝对地址，实践中用得不多。

Thymeleaf 模板

Thymeleaf 的特点是“自然模板”：指令都写成 HTML 属性（th:text、th:each…）， 所以模板文件本身就是合法的 HTML，直接用浏览器打开也能看到静态效果。代价是写法比 Django 的 {{ }}/{% %} 啰嗦。

模板继承：Layout Dialect

{# list.html #}

“过滤器”去哪了：自定义表达式对象

Thymeleaf 没有 |linebreaks 这种管道语法，但它有“表达式对象”（#strings、#lists、#temporals…）。 我们可以注册自己的表达式对象 #text，把 Django 的 linebreaks、truncatewords 实现成普通 Java 方法： 

@Component
public class TextFilters {

    /** {{ value|linebreaks }}：先转义 HTML，空行分段成 <p>，单个换行变 <br>。 */
    public String linebreaks(String value) {
        if (value == null || value.isBlank()) {
            return "";
        }
        String normalized = value.replace("\r\n", "\n").replace('\r', '\n').strip();
        return Arrays.stream(normalized.split("\n{2,}"))
                .map(p -> "<p>" + HtmlUtils.htmlEscape(p).replace("\n", "<br>") + "</p>")
                .collect(Collectors.joining("\n\n"));
    }

    /** {{ value|truncatewords:n }} */
    public String truncatewords(String value, int count) { ... }
}

@Component   // Spring Boot 会把所有 IDialect 类型的 Bean 自动注册到模板引擎
public class TextDialect extends AbstractDialect implements IExpressionObjectDialect {
    ...
    public IExpressionObjectFactory getExpressionObjectFactory() {
        return new IExpressionObjectFactory() {
            public Set<String> getAllExpressionObjectNames() { return Set.of("text"); }
            public Object buildObject(IExpressionContext ctx, String name) { return filters; }
            public boolean isCacheable(String name) { return true; }
        };
    }
}
🔎 为什么不直接在模板里写 ${@textFilters.linebreaks(...)}

Spring 的 SpEL 支持 @beanName 语法调用容器里的 Bean，老教程里很常见。 但 Thymeleaf 3.1 出于安全考虑，在 th:utext 等场景禁止了这类表达式（以及 T(...) 静态调用、new）， 会报 “Instantiation of new objects and access to static classes or parameters is forbidden”。 注册为表达式对象是官方推荐的扩展方式，也更像 Django 的“自定义过滤器库”。

管理后台：Django Admin 没有替代品

Django 写十几行 ModelAdmin，就有了带搜索、过滤、分页、表单校验、增删改的后台。 Spring 生态里没有这样的内置组件 —— 这是从 Django 转过来的人最不适应的地方。 本章手写了一个“迷你 admin”，URL 刻意模仿 Django：/admin/blog/post/、/admin/blog/post/add/、/admin/blog/post/1/change/。

其中最值得学的是 Specification —— 它就是 Spring Data 版的“动态拼 Q 对象”：

@GetMapping("/blog/post/")
public String list(@RequestParam(required = false) String q,
                   @RequestParam(required = false) PostStatus status,
                   @RequestParam(defaultValue = "1") int page, Model model) {

            PageRequest.of(Math.max(page, 1) - 1, PAGE_SIZE, ordering));
    model.addAttribute("page", result);
    model.addAttribute("draftCount", posts.countByStatus(PostStatus.DRAFT));
    model.addAttribute("publishedCount", posts.countByStatus(PostStatus.PUBLISHED));
    ...
}

/** search_fields + list_filter：条件为空就不加 */
static Specification<Post> filter(String q, PostStatus status) {
    return (root, query, cb) -> {
        List<Predicate> predicates = new ArrayList<>();
        if (q != null && !q.isBlank()) {
            String like = "%" + q.strip().toLowerCase() + "%";
            predicates.add(cb.or(
                    cb.like(cb.lower(root.get("title")), like),
                    cb.like(cb.lower(root.get("body")), like)));
        }
        if (status != null) {
            predicates.add(cb.equal(root.get("status"), status));
        }
        return cb.and(predicates.toArray(Predicate[]::new));
    };
}
ⓘ 表单对象 PostForm

Django admin 根据模型自动生成表单。Spring 里我们写一个单独的 PostForm 类接收提交的数据， 用 @NotBlank、@Size(max = 250)、@Pattern 声明规则；控制器参数上加 @Valid， 校验结果放在紧随其后的 BindingResult 里。为什么不直接绑定到实体上？ 因为那样用户可以通过多提交一个字段去修改本不该改的属性（“批量赋值”漏洞）。第 2 章会专门讲表单。

Spring Security：本章只用最小的一部分

原书第 1 章靠 Django Admin 自带的登录页进入后台，收藏功能依赖 request.user。 Spring 版需要自己提供三样东西：用户表、从表里加载用户的服务、哪些 URL 需要登录的规则。 

@Configuration
public class SecurityConfig {

    @Bean
    @ConditionalOnWebApplication   // 以命令行方式运行 createsuperuser 时不需要
    SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/admin/**").hasRole("STAFF")        // is_staff
                .requestMatchers("/blog/favourite/**", "/blog/favourites/**").authenticated()  // @login_required
                .anyRequest().permitAll())
            .formLogin(Customizer.withDefaults())   // 先用自带的登录页，第 4 章再自己写
            .logout(Customizer.withDefaults());
        return http.build();                        // CSRF 保护默认开启
    }

    @Bean
    PasswordEncoder passwordEncoder() {            // ≈ PASSWORD_HASHERS，默认 bcrypt
        return PasswordEncoderFactories.createDelegatingPasswordEncoder();
    }
}
  • JpaUserDetailsService 按用户名查 auth_user 表，返回一个 CurrentUser（实现了 UserDetails），它就是控制器里 @AuthenticationPrincipal CurrentUser me 拿到的对象 —— 对应 request.user。
  • is_staff / is_superuser 被翻译成权限 ROLE_STAFF / ROLE_ADMIN。
  • 用户表的表名和字段刻意沿用 Django 的 auth_user，方便对照。

复合主键：收藏功能

仓库第 1 章有一个 Django 5.2 新特性的彩蛋：FavouritePost 用 CompositePrimaryKey("user", "post") 做联合主键。 这在 Django 里是新功能，在 JPA 里则是老功能了：

@Entity
@Table(name = "blog_favouritepost")
public class FavouritePost {
    @EmbeddedId

    @MapsId("userId")      // 主键的 userId 就是这个外键列
    @ManyToOne(fetch = FetchType.LAZY)

    @MapsId("postId")

控制器里，收藏改成了 POST + 必须登录，并且只能收藏已发布的文章 —— 这正是 Django 版第 1 章代码点评里指出、并建议修复的三个问题：

@PostMapping("/favourite/add/{id}/")
public String addFavourite(@PathVariable Long id, @AuthenticationPrincipal CurrentUser me) {
    Post post = posts.findPublishedById(id)
            .orElseThrow(() -> new NotFoundException("No Post matches the given query."));
    FavouritePostId key = new FavouritePostId(me.id(), post.getId());
    if (!favourites.existsById(key)) {           // get_or_create 的“get”
        favourites.save(new FavouritePost(users.getReferenceById(me.id()), post));
    }
    return "redirect:" + post.getAbsoluteUrl();
}

💡 getReferenceById：只要外键，不查用户

保存收藏只需要用户的 id，不需要把整行用户数据查出来。getReferenceById 返回一个只带 id 的“代理对象”，不发 SELECT， 相当于 Django 里直接给外键赋 id：FavouritePost(user_id=request.user.id, post=post)。

测试：MockMvc

Django 仓库里的 tests.py 是空的。Spring 版每章都带测试，它们也是理解代码最快的入口。 @SpringBootTest 启动完整的应用上下文，MockMvc 在不开端口的情况下模拟 HTTP 请求 —— 作用和 Django 的 self.client 一样： 

@SpringBootTest
@AutoConfigureMockMvc
@ActiveProfiles("test")      // 使用 application-test.yaml：内存 H2
@Transactional               // 每个测试结束后回滚，≈ Django 的 TestCase
class BlogControllerTests {

    @Test
    void anonymousUserMustLogInBeforeAddingFavourite() throws Exception {
        mvc.perform(post("/blog/favourite/add/{id}/", published.getId()).with(csrf()))
                .andExpect(status().is3xxRedirection())
                .andExpect(redirectedUrl("/login"));
        assertThat(favourites.count()).isZero();
    }

    @Test
    void loggedInUserCanFavouriteOnlyOnce() throws Exception {
        var me = user(CurrentUser.from(author));          // ≈ self.client.force_login(user)
        for (int i = 0; i < 2; i++) {
            mvc.perform(post("/blog/favourite/add/{id}/", published.getId()).with(me).with(csrf()))
                    .andExpect(redirectedUrl(published.getAbsoluteUrl()));
        }
        assertThat(favourites.count()).isEqualTo(1);
    }
}

差异点评：Spring 版做了哪些取舍

🔍 第 1 章 Spring 版点评 springboot/Chapter01

做得好 表结构由 Flyway 管理，Hibernate 只校验

迁移脚本进版本库，启动时自动执行，ddl-auto: validate 能在实体和表不一致时第一时间报错。这是 Spring 项目里最稳妥的组合。

做得好 关闭 open-in-view，用 @EntityGraph 显式取数

模板渲染阶段不再偷偷发 SQL。N+1 从“悄悄变慢”变成“直接报错”，问题暴露得更早。Django 版原代码的列表页其实就有 N+1（没写 select_related）。

做得好 修复了 Django 版点评里的收藏问题

改为 @PostMapping + 登录要求 + CSRF，且只能收藏已发布文章，URL 的拼写错误 favrourite 也改正了。测试覆盖了“匿名用户被重定向”和“缺少 CSRF 返回 403”。

注意 代码量明显多于 Django

同样的功能，Django 版的模型、视图、URL 和 admin 一共约 150 行 Python；Spring 版约 1100 行 Java 加 280 行模板（含大量教学注释，其中约 400 行是手写后台，还有不少 getter/setter）。 这是静态类型 + 显式配置的代价。可以用 Lombok 或把简单实体改成 Kotlin 来减少样板代码，本书为了让初学者看清每一行在做什么，没有使用。

注意 时间与时区

Django 开启 USE_TZ 后存的是带时区的 UTC 时间。Java 这边用 OffsetDateTime + 列类型 TIMESTAMP WITH TIME ZONE， 并设置 hibernate.jdbc.time_zone: UTC。后台的 datetime-local 输入框没有时区信息，我们约定按 UTC 解释，并在标签上注明“(UTC)”。 真实项目应当按用户所在时区换算。

补充知识 Java 生态里有没有“自动后台”

有一些方向可以减少手写量：Spring Data REST 能把仓库直接暴露成 REST 接口，再配一个通用前端； JHipster 之类的代码生成器能生成带增删改查页面的项目。但它们都不是 Django Admin 那种“注册一个类就完事”的体验。 对内部后台，很多团队的选择就是像本章这样，手写少量页面。

小结

  • Spring MVC 的请求路线：过滤器链 → DispatcherServlet → 控制器 → 仓库 → 视图名 + Model → Thymeleaf。
  • “装应用”靠包扫描和 starter 依赖；配置写在 application.yaml。
  • 实体用 JPA 注解描述；注意 nullable = false、LAZY、枚举的存储方式。
  • 迁移用 Flyway 手写 SQL，Hibernate 只做 validate。
  • 仓库接口：方法名派生查询、default 方法封装常用条件、@Query 写 JPQL、Specification 做动态条件、@EntityGraph 防 N+1。
  • 控制器方法 = 视图函数 + URL 规则；找不到数据抛 404 异常。
  • Thymeleaf 用 Layout Dialect 实现继承；过滤器用自定义表达式对象代替。
  • 没有 Django Admin，后台要自己写；Spring Security 负责登录与权限。
