部署补充：更简单、可重复的上线

第 17 章搭了一套完整的自建环境：Nginx + uWSGI + Daphne，静态文件和媒体文件都放在服务器磁盘上，迁移和收集静态文件靠手工执行。 它很好地展示了各个组件的分工，但维护起来零件多、步骤多。这一篇介绍今天更常见的做法：用 Gunicorn 统一运行、WhiteNoise 发送静态文件、 对象存储保存用户上传，再加上健康检查、可重复构建的镜像和自动化部署流程。

本篇目标

  • 对比第 17 章的方案与一种更精简的方案，理解各自的取舍
  • 用 Gunicorn（+ Uvicorn worker）运行 WSGI 或 ASGI 应用，合理设置进程数
  • 用 WhiteNoise 发送静态文件，用 django-storages 把媒体文件放到对象存储
  • 写健康检查端点，并避开 ALLOWED_HOSTS 和 HTTPS 重定向的坑
  • 写一个可重复构建的生产 Dockerfile，理解“构建 → 迁移 → 发布”的顺序
  • 用 GitHub Actions 自动构建镜像并部署；准备好 Celery 进程、备份和回滚方案

两种架构

Gunicorn：应用服务器

Gunicorn 是 Python 社区最常用的应用服务器：一个主进程管理多个 worker 进程，worker 挂了自动重启。 默认 worker 运行 WSGI；换成 uvicorn_worker.UvicornWorker 就能运行 ASGI，同时处理 HTTP 和第 16 章的 WebSocket。 第 17 章用的 uWSGI 目前处于维护模式，新项目一般不再选它。 

import os

bind = '0.0.0.0:8000'
workers = int(os.environ.get('WEB_CONCURRENCY', 3))
worker_class = 'uvicorn_worker.UvicornWorker'     # 运行 ASGI（含 Channels）；纯 WSGI 项目删掉这一行
timeout = 30
accesslog = '-'                                    # 访问日志输出到 stdout

python -m pip install gunicorn uvicorn-worker
gunicorn config.asgi:application -c gunicorn.conf.py     # ASGI
gunicorn config.wsgi:application -c gunicorn.conf.py     # 或者 WSGI
ⓘ 反向代理后面要告诉 Django“原本是 HTTPS”

TLS 在代理上终结后，Django 收到的是 HTTP。代理要设置 X-Forwarded-Proto 头，Django 里配置 SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO', 'https')，否则 SECURE_SSL_REDIRECT 会陷入无限重定向。只有当代理一定会覆盖这个头时才能这样设置，否则客户端可以伪造它。

💡 媒体文件为什么最好放在别的域名

用户上传的文件如果和网站同源，一个伪装成图片的 HTML 或 SVG 文件就可能在你的域名下执行脚本。对象存储自带独立域名，这类风险自然就没有了（专题 6）。

健康检查

负载均衡器、容器平台会定期访问一个地址，确认进程还活着；不健康的实例会被摘掉流量或重启。健康检查有两个常见的坑：

  • 探测请求通常直接用 IP 访问，Host 不在 ALLOWED_HOSTS 里，Django 返回 400；
  • 探测走的是 HTTP，SECURE_SSL_REDIRECT 把它 301 到 HTTPS，探测判定失败。

第 17 章点评里，子域名中间件还会把 IP 访问变成 404。最省事的做法是在中间件列表最前面直接回答健康检查，在所有这些检查之前返回：

from django.db import connection
from django.http import HttpResponse


class HealthCheckMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        if request.path == '/healthz/':
            return HttpResponse('ok')
        if request.path == '/readyz/':
            try:
                connection.ensure_connection()
            except Exception:
                return HttpResponse('database unavailable', status=503)
            return HttpResponse('ok')
        return self.get_response(request)

# settings: MIDDLEWARE = ['core.middleware.HealthCheckMiddleware', 'django.middleware.security.SecurityMiddleware', ...]

可重复构建的生产镜像

第 17 章点评指出，生产环境把源码目录挂载进容器、以 root 运行、没有 .dockerignore。下面是一个按专题 2 项目骨架写的生产 Dockerfile：

FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    UV_COMPILE_BYTECODE=1 \
    UV_LINK_MODE=copy \
    PATH="/app/.venv/bin:$PATH"

# 正式使用时把 latest 换成固定版本（Dockerfile 只支持整行注释，不能写在指令后面）
COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/
WORKDIR /app

# 先只复制依赖声明：依赖不变时这一层直接用缓存
COPY pyproject.toml uv.lock ./
RUN uv sync --locked --no-dev

COPY . .

# 构建时收集静态文件；这里的密钥和数据库只是为了让设置能加载
RUN DJANGO_SETTINGS_MODULE=config.settings.production \
    DJANGO_SECRET_KEY=build-only DATABASE_URL=sqlite://:memory: \
    python manage.py collectstatic --noinput

# 不以 root 运行
RUN useradd --create-home app
USER app

EXPOSE 8000
CMD ["gunicorn", "config.asgi:application", "-c", "gunicorn.conf.py"]

发布流程：构建 → 迁移 → 切换

name: Deploy
on:
  workflow_run:
    workflows: [CI]                 # 专题 1 的测试工作流成功后才部署
    types: [completed]
    branches: [main]

jobs:
  build:
    if: ${{ github.event.workflow_run.conclusion == 'success' }}
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.event.workflow_run.head_sha }}
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          push: true
          tags: ghcr.io/your-name/mysite:${{ github.event.workflow_run.head_sha }}   # 镜像名必须全小写

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.DEPLOY_HOST }}
          username: deploy
          key: ${{ secrets.DEPLOY_SSH_KEY }}
          script: |
            cd /srv/mysite
            export IMAGE_TAG=${{ github.event.workflow_run.head_sha }}
            docker compose pull
            docker compose run --rm web python manage.py migrate --noinput
            docker compose run --rm web python manage.py setup_groups
            docker compose up -d

services:
  web:
    image: ghcr.io/your-name/mysite:${IMAGE_TAG}
    env_file: .env.production
    ports: ["127.0.0.1:8000:8000"]        # 只对本机的反向代理开放
    restart: unless-stopped
  worker:
    image: ghcr.io/your-name/mysite:${IMAGE_TAG}
    env_file: .env.production
    command: celery -A config worker -l info --concurrency 2
    restart: unless-stopped
  beat:
    image: ghcr.io/your-name/mysite:${IMAGE_TAG}
    env_file: .env.production
    command: celery -A config beat -l info    # 定时任务调度器：全局只能运行一个
    restart: unless-stopped
ⓘ 不想自己管服务器？

Render、Fly.io、Railway 这类平台（PaaS）替你做了 TLS、负载均衡、滚动发布和健康检查，通常只需要声明三类进程：web（Gunicorn）、worker（Celery）和 release（每次发布前运行的 migrate）。数据库和 Redis 也可以用平台托管的。小团队的第一个项目，这往往是成本最低的选择。

备份与回滚

# 每天备份（cron 或平台的定时任务），保存到另一台机器或对象存储
pg_dump --format=custom "$DATABASE_URL" > "backup-$(date +%F).dump"

# 恢复到一个新库，定期演练一次
pg_restore --no-owner --dbname "$RESTORE_DATABASE_URL" backup-2026-09-13.dump
  • 没有演练过恢复的备份，等于没有备份。托管数据库一般提供时间点恢复（PITR），也要确认怎么用。
  • 媒体文件在对象存储里，打开版本控制或定期同步到另一个桶。
  • 代码回滚靠镜像标签；数据回滚靠备份。这就是为什么删除数据的迁移要格外小心（专题 5）。

上线清单

  1. python manage.py check --deploy 没有警告；DEBUG = False；所有机密来自环境变量。
  2. 本次发布的迁移都向后兼容，已经用 sqlmigrate 看过危险操作的 SQL。
  3. 镜像在 CI 中构建，静态文件在构建时收集，容器以非 root 用户运行。
  4. 媒体文件在对象存储中；上传大小限制在代理和 Django 两处都配置好。
  5. /healthz/ 和 /readyz/ 可用，平台或负载均衡已配置健康检查。
  6. 日志输出到 stdout，错误能到达 Sentry 或管理员邮箱（专题 3）。
  7. Celery worker 和 beat 已部署，beat 只有一个实例。
  8. 数据库每日备份，恢复流程演练过；知道如何把镜像切回上一个版本。

🔍 第 17 章部署方案的再审视 Chapter17/

做得好 组件分工讲得很清楚

第 17 章把 TLS、静态文件、WSGI、ASGI 各自交给谁处理讲得非常清楚，理解了这套分工，再看任何平台的部署文档都不会陌生。本篇的精简方案只是把其中几项交给了现成的工具或平台。

建议改进 媒体文件存在单台服务器的磁盘上

讲师上传的课程文件保存在挂载的 media/ 目录里。一旦要加第二台服务器、换机器，或者磁盘损坏，文件就会不同步或丢失。改用 django-storages 保存到对象存储。

建议改进 两套应用服务器、手工发布步骤

uWSGI 与 Daphne 各自一套配置；migrate、collectstatic 靠 docker compose exec 手工执行。用 Gunicorn + Uvicorn worker 统一成一种进程，把发布步骤写进流水线，每次都一样。

建议改进 没有健康检查，也没有 Celery 进程

Compose 文件里没有健康检查，容器“启动了但不能用”时不会被发现；第 8 章起依赖的 Celery worker 也没有出现在生产环境里，下单确认邮件、支付发票都不会被发送。

补充知识 什么时候需要 Kubernetes

多数项目在一台服务器或一个 PaaS 上就能跑很久。只有需要在多台机器间自动调度大量服务时，Kubernetes 的复杂度才值得。本篇的做法（无状态进程、健康检查、镜像标签、向后兼容的迁移）换到 Kubernetes 上完全适用。

小结

  • Gunicorn 管理多个 worker；配合 Uvicorn worker 可以用一种进程同时处理 HTTP 和 WebSocket。
  • 静态文件在构建时收集、由 WhiteNoise 发送；媒体文件放对象存储，应用进程保持无状态。
  • 健康检查中间件放在最前面，避开主机校验和 HTTPS 重定向。
  • 镜像在 CI 中构建、带提交哈希标签；发布顺序是“迁移 → 替换进程”，迁移必须向后兼容。
  • 备份要演练恢复；代码回滚靠镜像标签，数据回滚靠备份。
