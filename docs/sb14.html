Spring Boot 版 · 第 14 章 · 项目四：在线学习平台

渲染与缓存内容

平台终于有了学生这一端：公开的课程目录、学生注册（注册后自动登录）、选课、按模块学习课程内容。 内容有四种类型，各自需要不同的 HTML（视频要嵌入播放器）。页面访问量大、内容变化少，于是书中引入了 Django 的缓存框架，用 Redis 存放查询结果。 Spring 的缓存抽象用注解声明“这个方法的结果可以缓存”，比手写 cache.get / cache.set 简洁； 但它也有自己的坑 —— 事务、代理、异步清除 —— 这一章都会遇到。另外，书中的缓存从不失效，我们会把这个问题补上。

本章目标

  • 用 JPQL 构造器表达式查出“课程 + 模块数”这样的汇总 DTO（≈ annotate(Count(...))）
  • 学生注册后以编程方式登录：保存 SecurityContext、更换会话 id
  • 用 Thymeleaf 片段按类型渲染内容（≈ item.render()），自己实现视频嵌入
  • 用 @Cacheable / @CacheEvict + Redis 缓存目录和模块内容，并在内容变化时清除
  • 理解事务感知缓存、代理自调用、Lettuce 异步清除这三个坑

对应的 Django 讲解见 Django 版第 14 章；本章代码在 springboot/Chapter14/。

全景：读走缓存，写清缓存

公开课程目录

首页列出所有学科（带课程数）和课程（带模块数、讲师），可以按学科筛选；课程详情页有“选课”按钮。 书中用 annotate(total_courses=Count('courses')) 给模型对象附加一个计数属性。JPA 里对应的写法是构造器表达式： 直接把查询结果装进一个 record，这个 DTO 后面正好可以放进缓存。

Django · CourseListView
subjects = Subject.objects.annotate(
    total_courses=Count('courses'))
all_courses = Course.objects.annotate(
    total_modules=Count('modules'))
if subject:
    subject = get_object_or_404(Subject, slug=subject)
    courses = all_courses.filter(subject=subject)
Spring · CourseRepository
@Query("""
    select new com.example.educa.courses.catalog.CourseSummary(
        c.id, c.title, c.slug, s.title, s.slug,
        o.username, o.firstName, o.lastName, count(m))
    from Course c join c.subject s join c.owner o
         left join c.modules m
    where :subjectSlug is null or s.slug = :subjectSlug
    group by c.id, c.title, c.slug, s.title, s.slug,
             o.username, o.firstName, o.lastName, c.created
    order by c.created desc
    """)
List<CourseSummary> summaries(@Param("subjectSlug") String subjectSlug);
  • left join c.modules m + count(m)：没有模块的课程也会出现，计数为 0（和 Count 的行为一致）。
  • 学科的课程数：Subject 实体上没有 courses 集合，用 JPQL 的实体连接 left join Course c on c.subject = s —— 不必为了一个查询去声明反向关系。
  • where :subjectSlug is null or ... 让一个查询同时服务“全部”和“按学科”两种情况。
⚠ /course/{slug}/ 和 /course/mine/ 共享前缀

课程详情是 /course/<slug>/，讲师后台是 /course/mine/、/course/create/。 Spring MVC 会优先匹配字面量更多的模式，所以两者不冲突（slug 恰好叫 mine 的课程就访问不到了，Django 按顺序匹配也一样）。 但 Spring Security 的 URL 规则是从上到下、第一条命中生效，顺序必须写对： 

.requestMatchers("/course/subject/**").permitAll()
.requestMatchers("/course/mine/", "/course/create/").authenticated()
.requestMatchers("/course/*/").permitAll()                  // 课程详情：只有一段
.requestMatchers("/students/register/").permitAll()
.requestMatchers("/course/**", "/students/**").authenticated()

学生注册与自动登录

Django · StudentRegistrationView
class StudentRegistrationView(CreateView):
    form_class = UserCreationForm
    success_url = reverse_lazy('student_course_list')

    def form_valid(self, form):
        result = super().form_valid(form)
        cd = form.cleaned_data
        user = authenticate(username=cd['username'],
                            password=cd['password1'])
        login(self.request, user)
        return result
Spring · StudentController
User user = service.register(form);
login(CurrentUser.from(user), request, response);
return "redirect:/students/courses/";

private void login(CurrentUser principal,
        HttpServletRequest request, HttpServletResponse response) {
    var auth = UsernamePasswordAuthenticationToken.authenticated(
            principal, null, principal.getAuthorities());
    SecurityContext context = SecurityContextHolder.createEmptyContext();
    context.setAuthentication(auth);
    SecurityContextHolder.setContext(context);
    if (request.getSession(false) != null) {
        request.changeSessionId();          // 防会话固定
    }
    securityContextRepository.saveContext(context, request, response);
}

Django 的 login() 一行做了三件事，自己写的时候一件都不能少：

  1. 把认证结果放进 SecurityContext —— 只做这一步，当前请求是“已登录”的；
  2. 保存到会话 —— Spring Security 6 起，SecurityContextHolder 的修改不会再自动写回会话，必须显式调用 SecurityContextRepository.saveContext()，否则重定向后的下一个请求又是匿名的。所以要把仓库声明成 Bean，并在过滤器链里用同一个；
  3. 更换会话 id —— 登录前后用同一个会话 id 会导致会话固定攻击（攻击者先把一个已知的会话 id 塞给受害者）。Django 的 login() 内部调用 cycle_key()；Servlet 的对应物是 request.changeSessionId()。

注册表单对应 UserCreationForm：用户名只能包含字母、数字和 @/./+/-/_，且唯一； 密码规则对应 AUTH_PASSWORD_VALIDATORS 里的“至少 8 位”和“不能全是数字”（相似度和常见密码两个校验器没有实现）； 两次密码不一致的错误挂在 password2 上。密码用 PasswordEncoder（默认 bcrypt）哈希后保存。

按类型渲染内容

书中给 ItemBase 加了一个 render() 方法：render_to_string(f'courses/content/{self._meta.model_name}.html', {'item': self})， 模板里写 {{ item.render }}。Thymeleaf 可以直接做到“按名字选择片段”，不需要在实体里调用模板引擎：

Django · 模板
{% for content in module.contents.all %}
  {% with item=content.item %}
    <h2>{{ item.title }}</h2>
    {{ item.render }}
  {% endwith %}
{% endfor %}

{# courses/content/video.html #}
{% load embed_video_tags %}
{% video item.url "small" %}
Spring · 模板
<th:block th:each="item : ${contents}">
  <h2 th:text="${item.title}">Title</h2>
  <th:block th:replace="~{courses/content/__${item.modelName}__
                         :: item(${item})}"></th:block>
</th:block>

<!-- courses/content/video.html -->
<th:block th:fragment="item(item)">
  <iframe th:if="${item.embedUrl}" th:src="${item.embedUrl}"
          width="480" height="360" allowfullscreen></iframe>
  <p th:unless="${item.embedUrl}"><a th:href="${item.url}"
     th:text="${item.url}">video</a></p>
</th:block>
  • __${item.modelName}__ 又是预处理：先得到 text，再解析 ~{courses/content/text :: item(...)}。modelName 来自我们自己的代码而不是用户输入，所以不存在模板注入的问题。
  • 模板拿到的是 ContentView record 而不是实体：它在事务里从实体转换而来，可以序列化进缓存；视频的嵌入地址也在转换时算好。
  • django-embed-video 能识别 YouTube、Vimeo 等网站。Java 没有同类的常用库，这里写了一个 VideoEmbed：用 URI 解析地址，只认 youtube.com/watch?v=、youtu.be/、/shorts/ 和 vimeo.com/数字，视频 id 还要匹配 [A-Za-z0-9_-]{11}，认不出的一律退化为普通链接。
  • 文字内容用 #text.linebreaks()（先转义 HTML，再把空行变成段落），和 {{ item.content|linebreaks }} 一样安全。
⚠ 懒加载的 item 是代理，switch 匹配会失败

转换 DTO 时写了 switch (item) { case TextItem t -> ... }。学习页面的查询用 @EntityGraph("item") 把条目一起查出来，拿到的是真实的子类对象； 但在别的路径上（比如下一章的 API），content.getItem() 返回的是 Item 的 Hibernate 代理，所有 case 都不匹配。 所以转换前先 Hibernate.unproxy(item)。

Spring · 注解声明在服务方法上
@Service
@Transactional(readOnly = true)
public class CatalogService {

    @Cacheable(cacheNames = "subjects", key = "'all'")
    public List<SubjectSummary> subjects() {
        return subjects.summaries();
    }

    @Cacheable(cacheNames = "courses", key = "#subjectSlug ?: 'all'")
    public List<CourseSummary> courses(String subjectSlug) {
        return courses.summaries(subjectSlug);
    }

    @Cacheable(cacheNames = "moduleContents", key = "#moduleId")
    public List<ContentView> moduleContents(Long moduleId) { ... }
}

spring:
  cache:
    type: redis
    redis:
      time-to-live: 15m          # ≈ CACHE_MIDDLEWARE_SECONDS = 60 * 15
      key-prefix: "educa::"      # ≈ CACHE_MIDDLEWARE_KEY_PREFIX
  • Redis 里的键是 educa::courses::all、educa::moduleContents::3（前缀 + 缓存名 + 键）。开发时 spring-boot-docker-compose 会按 compose.yaml 自动启动 Redis。
  • 缓存 DTO，不缓存实体。书中缓存的是 QuerySet（pickle 时会求值），反序列化出来的对象脱离了数据库连接；实体更糟 —— 里面有 Hibernate 代理和懒加载集合，序列化时要么报错、要么把半个数据库拖进缓存。record 简单、不可变、实现 Serializable 即可。
  • 书中的 if not subjects 把“空列表”也当作未命中，每次都查库；@Cacheable 用的是“有没有这个键”，空列表同样会被缓存。

补上缓存失效

书中只写入缓存，从不清除：讲师新建了课程，首页最多要等 15 分钟才看得到；修改了模块内容，学生看到的还是旧的。 在写操作上声明清除即可 —— 这是“声明式”最大的好处，读和写的缓存规则都在方法签名上一目了然： 

/** 组合注解：课程增删改后清空“学科列表”和“课程列表” */
@Target(METHOD) @Retention(RUNTIME)
@Caching(evict = {
        @CacheEvict(cacheNames = CacheNames.SUBJECTS, allEntries = true),
        @CacheEvict(cacheNames = CacheNames.COURSES, allEntries = true)
})
public @interface EvictCatalog { }

@EvictCatalog
public Course createCourse(Long ownerId, CourseForm form) { ... }

@CacheEvict(cacheNames = CacheNames.MODULE_CONTENTS, key = "#moduleId")
public Item saveItem(Long moduleId, String modelName, Long itemId, Long ownerId, ItemForm form) { ... }

public Long deleteContent(Long contentId, Long ownerId) {
    ...
    // 模块 id 要查出内容之后才知道，注解里写不出 key：用编程方式清除
    cacheManager.getCache(CacheNames.MODULE_CONTENTS).evict(moduleId);
}

三个坑

⚠ 坑一：先清缓存、后提交事务

@CacheEvict 在方法返回时执行，而 @Transactional 在更外层，事务还没提交。 这个空档里另一个请求读缓存未命中，去数据库读到的还是旧数据，又写回缓存 —— 清除白做了。 解决办法是让缓存管理器“事务感知”：事务中的写入和清除推迟到提交之后才真正作用到 Redis。 

@Bean
RedisCacheManagerBuilderCustomizer cacheManagerCustomizer(RedisConnectionFactory cf) {
    return builder -> builder
            .cacheWriter(RedisCacheWriter.create(cf, writer -> writer.immediateWrites()))
            .transactionAware();
}

副作用：在 @Transactional 的测试里（最后回滚、永不提交），缓存写入永远不会发生。所以缓存行为要在不加 @Transactional 的测试类里验证，自己清理数据。

⚠ 坑二：清空缓存默认是异步的

第一版测试里，讲师新建课程后立即断言 educa::subjects::all 已被删除 —— 失败了，键还在。 原因是 Spring Data Redis 4 配合 Lettuce 驱动时，allEntries = true 触发的 clear() 默认异步执行 （Spring 的 Cache.clear() 约定本来就允许异步或延迟执行，需要立即生效时应该用 invalidate()）。 重定向之后的下一个请求可能仍然读到旧列表。上面配置里的 immediateWrites() 把写入和清除改为同步。

⚠ 坑三：同一个类里调用不经过缓存

@Cacheable 和 @Transactional 一样靠代理实现：只有从别的 Bean 调用才会经过缓存逻辑， 同一个类里 this.subjects() 直接调用的是原始方法。这也是把缓存方法单独放进 CatalogService 的原因。

差异点评

🔍 第 14 章 Spring 版点评 springboot/Chapter14

做得好 缓存会失效

所有写操作都声明了清除，而且在事务提交之后才清除；学生不会在 15 分钟内看到过期内容。

做得好 手动登录的三个步骤一个不少

保存 SecurityContext、写回会话、更换会话 id；测试用同一个会话访问下一个页面，验证登录状态确实保存下来了。

注意 没有整页缓存

书中对学生学习页面用了 cache_page。Spring 没有对应物，这里只缓存了模块内容这一块数据。如果真的需要整页缓存，更好的做法是在 Nginx 或 CDN 层按 URL 缓存，并注意不能缓存带用户信息的页面。

注意 缓存里的类变了怎么办

JDK 序列化对类结构很敏感：部署新版本后，如果 ContentView 加了字段，Redis 里的旧数据反序列化会失败。简单的办法是部署时清空缓存或更换 key-prefix；也可以改用 JSON 序列化，对字段增减更宽容。

补充知识 为什么不缓存“学生的课程页面”整体

页面里有“哪个模块被选中”“这个学生能看什么”等个性化信息。缓存粒度应该落在“所有人都一样”的数据上：模块内容对所有选了这门课的学生都相同，所以按模块 id 缓存。

小结

  • 汇总查询用 JPQL 构造器表达式直接得到 DTO，既省去 N+1，又方便缓存。
  • 手动登录：SecurityContext + SecurityContextRepository.saveContext() + changeSessionId()。
  • 按类型渲染：~{courses/content/__${type}__ :: item(...)}；实体先转换成 DTO，注意 unproxy。
  • @Cacheable 读、@CacheEvict 写；缓存管理器要事务感知、同步写入；缓存方法要从别的 Bean 调用。
