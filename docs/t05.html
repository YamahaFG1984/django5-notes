迁移深入：安全地改数据库

书里的迁移总是两步：makemigrations、migrate。开发时数据库随时可以删掉重建，这样做没问题； 可一旦库里有了真实数据，迁移就成了最容易出事故的操作之一。第 11 章的翻译迁移会直接删掉商品名称，第 5 章的模型与迁移对不上， 第 12 章的自定义字段在迁移里丢了参数。这一篇讲迁移的原理，以及数据迁移、回滚、冲突和上线不停机的做法。

本篇目标

  • 理解迁移文件、依赖图和 django_migrations 表之间的关系
  • 熟练使用 showmigrations、sqlmigrate、migrate --plan、makemigrations --check 和回滚
  • 写出可逆的数据迁移，知道为什么要用 apps.get_model()
  • 用“扩展 → 迁移数据 → 收缩”三步安全地重构模型
  • 处理多人协作时的迁移冲突，用 squashmigrations 压缩历史
  • 知道哪些操作会锁表或让旧代码报错，以及上线不停机的替代写法

依赖图、冲突与合并

💡 合并之前先想一想

如果两个分支的迁移互不相干（一个加标签表、一个加点赞字段），makemigrations --merge 生成的空合并迁移就够了。 如果它们改了同一张表的同一个字段，就要人工检查执行顺序是否影响结果。另一个常见做法是：合并代码前先 rebase，删掉自己分支里还没在任何共享环境执行过的迁移，重新生成。

回滚与“不可逆”

每个迁移操作都知道怎么“倒着做”：AddField 的反向是删字段，CreateModel 的反向是删表。migrate blog 0002 会按相反顺序撤销 0002 之后的所有迁移。但有两类操作倒不回去：

  • 删除字段或表：结构可以恢复，数据不会回来。回滚只是再加一个空列。
  • 没有写反向函数的 RunPython / RunSQL：Django 会拒绝回滚并报 IrreversibleError。
⚠ 回滚不能代替备份

对生产库执行任何删除数据的迁移前，先确认有可用的备份（专题 7）。回滚迁移能恢复“结构”，只有备份能恢复“数据”。

数据迁移：RunPython

结构迁移改表，数据迁移改表里的数据：给老数据填新字段、拆分字段、把数据搬到新表。用 makemigrations --empty 生成一个空迁移，再写 RunPython：

python manage.py makemigrations blog --empty --name backfill_reading_time

from django.db import migrations


def forwards(apps, schema_editor):
    Post = apps.get_model('blog', 'Post')          # 历史模型：迁移执行到这一步时的样子
    posts = list(Post.objects.only('id', 'body'))
    for post in posts:
        post.reading_time = max(1, len(post.body.split()) // 200)
    Post.objects.bulk_update(posts, ['reading_time'], batch_size=500)


def backwards(apps, schema_editor):
    Post = apps.get_model('blog', 'Post')
    Post.objects.update(reading_time=None)


class Migration(migrations.Migration):
    dependencies = [('blog', '0004_post_reading_time')]
    operations = [migrations.RunPython(forwards, backwards)]
    # 反向确实什么都不用做时：migrations.RunPython(forwards, migrations.RunPython.noop)
ⓘ 大表的数据迁移

一个迁移默认在一个事务里执行。几百万行的回填会长时间持锁，最好用 .iterator() 分批处理，或者干脆写成管理命令在迁移之外分批执行，迁移本身只改结构。

三步重构：扩展 → 迁移数据 → 收缩

第 11 章把商品模型改成可翻译模型时，自动生成的 0002_translations 在同一个迁移里做了两件事：建翻译表，并删掉 Product 的 name、slug、description 列。在一个已经有商品的库上执行，所有商品名称就没了。

from django.conf import settings
from django.db import migrations


def copy_to_translations(apps, schema_editor):
    Product = apps.get_model('shop', 'Product')
    ProductTranslation = apps.get_model('shop', 'ProductTranslation')
    ProductTranslation.objects.bulk_create([
        ProductTranslation(
            master_id=p.pk,
            language_code=settings.LANGUAGE_CODE,
            name=p.name, slug=p.slug, description=p.description,
        )
        for p in Product.objects.all()          # 历史模型里 name 仍然是普通的列
    ])


def delete_translations(apps, schema_editor):
    apps.get_model('shop', 'ProductTranslation').objects.all().delete()


class Migration(migrations.Migration):
    dependencies = [('shop', '0002_add_translations')]
    operations = [migrations.RunPython(copy_to_translations, delete_translations)]

自定义字段与迁移：deconstruct()

迁移文件里的字段是靠 deconstruct() “描述”出来的：Django 调用它得到“类路径 + 参数”，写进迁移。 第 12 章的 OrderField 在 __init__ 里接收 for_fields，却没有实现 deconstruct()， 所以生成的迁移里只有 OrderField(blank=True, default=0)：for_fields 丢了。好在这个参数只在运行时使用，模型代码里还有它； 可如果某个参数会影响数据库结构，迁移就会和模型不一致。 

class OrderField(models.PositiveIntegerField):
    def __init__(self, for_fields=None, *args, **kwargs):
        self.for_fields = for_fields
        super().__init__(*args, **kwargs)

    def deconstruct(self):
        name, path, args, kwargs = super().deconstruct()
        if self.for_fields is not None:
            kwargs['for_fields'] = self.for_fields      # 写进迁移，重放时原样还原
        return name, path, args, kwargs

python manage.py squashmigrations courses 0001 0040
ⓘ 压缩时的注意事项

含有 RunPython 的迁移会被原样搬进压缩后的文件，函数要能被导入（不能是 lambda）；压缩结果一定要人工检查，并在一个全新的空库上完整跑一遍 migrate 和测试。

上线不停机：哪些操作危险

滚动部署时，新旧两个版本的代码会同时运行一段时间，而数据库只有一个。部署顺序一般是“先迁移、再换代码”， 所以每个迁移都必须让旧代码也能继续工作：

操作风险更安全的做法
新增可空字段基本安全—
新增非空字段并给 Python defaultDjango 加列后会去掉数据库默认值，旧代码插入时不带这一列 → 报错用 5.0 的 db_default，默认值留在数据库里
删除字段旧代码的 SELECT 还带着这一列 → 报错先部署不再使用它的代码；列在下一个版本再删（可用 SeparateDatabaseAndState 先只从模型里移除）
重命名字段或表同上按图 T5-6 分三次部署
大表加索引建索引期间锁住写入PostgreSQL 用 AddIndexConcurrently
修改字段类型可能重写整张表并锁表新建列、回填、切换、删除旧列
新增唯一约束已有重复数据时迁移失败先写数据迁移清理重复，再加约束
from django.contrib.postgres.operations import AddIndexConcurrently
from django.db import migrations, models


class Migration(migrations.Migration):
    atomic = False                      # CONCURRENTLY 不能在事务里执行，必须关闭

    dependencies = [('blog', '0005_backfill_reading_time')]
    operations = [
        AddIndexConcurrently('post', models.Index(fields=['status', '-publish'], name='blog_post_status_pub_idx')),
    ]

operations = [
    migrations.SeparateDatabaseAndState(
        state_operations=[migrations.RemoveField('product', 'legacy_code')],   # Django 认为字段没了
        database_operations=[],                                               # 数据库什么都不做
    ),
]

团队约定

  1. 迁移文件和对应的模型改动在同一个提交里；CI 运行 makemigrations --check。
  2. 不修改、不删除已经在任何共享环境（测试服、生产）执行过的迁移；要改就写一个新迁移。
  3. 生成后读一遍迁移文件，对危险操作运行 sqlmigrate 看 SQL。
  4. 迁移里不导入模型，用 apps.get_model()；RunPython 尽量写反向函数。
  5. 结构迁移和大批量数据修改分开；删除数据前先备份。
  6. 每个迁移都要让上一个版本的代码继续可用。
ⓘ --fake 什么时候用

migrate app 0003 --fake 只在 django_migrations 表里记一笔，不执行 SQL。它用于“数据库结构其实已经是这样了”的场景，例如手工修复过数据库，或者接管一个已有的库（--fake-initial）。平时用它跳过报错的迁移，只会让模型、迁移和数据库三者对不上。

补充知识 书中的练习方式与真实项目的差别

书里遇到迁移问题时，常见做法是删掉数据库重新来过，学习时这完全没问题。真实项目里数据库永远不能删，所以本篇的每一个技巧，都是在“数据必须保留”这个前提下才需要的。

小结

  • 迁移文件是数据库结构的源代码：makemigrations 对比模型与迁移，migrate 对比迁移与 django_migrations 表。
  • 用 showmigrations、sqlmigrate、--plan、--check 看清楚再执行；回滚恢复不了被删除的数据。
  • 数据迁移用 RunPython + apps.get_model()，写好反向函数，大表分批。
  • 重构模型用“扩展 → 迁移数据 → 收缩”；多人冲突用 --merge；历史太长用 squashmigrations。
  • 不停机上线的核心是：每个迁移都让旧代码继续可用。
