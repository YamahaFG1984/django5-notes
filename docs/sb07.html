Spring Boot 版 · 第 7 章 · 项目二：图片书签社交网站

追踪用户行为

社交网站项目的最后一章：用户可以互相关注，仪表盘上出现“关注的人最近做了什么”的活动流； 点赞数用冗余字段维护，图片浏览数和排行榜交给 Redis。Django 版在这里用到了自关联的多对多、GenericForeignKey、 信号和 Debug Toolbar，它们在 Spring 里分别变成“中间实体”、“类型 + id”、应用事件和 SQL 日志 + Actuator。

本章目标

  • 把“带额外字段的多对多”建模成中间实体，实现关注 / 取消关注
  • 用“类型名 + id”实现 GenericForeignKey，并批量加载异构目标，避免 N+1
  • 用 ApplicationEventPublisher + @EventListener 替代 Django 信号，理解同步、事务内、事务后的区别
  • 在没有 Debug Toolbar 的情况下观察 SQL、映射表和配置
  • 用 StringRedisTemplate 做计数器和有序集合排行，用 Testcontainers 测试

对应的 Django 讲解见 Django 版第 7 章；本章代码在 springboot/Chapter07/。

关注系统：中间实体

Django 版定义了 Contact 模型，再通过 add_to_class 给内置的 User 动态加上一个 following 字段：

Spring · account/Contact.java
@Entity
@Table(name = "account_contact",
    indexes = @Index(name = "account_contact_created_idx",
                     columnList = "created DESC"),
    uniqueConstraints = @UniqueConstraint(
        name = "account_contact_from_to_uniq",
        columnNames = {"user_from_id", "user_to_id"}))
public class Contact {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "user_from_id")
    private User userFrom;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)

  • 加了 (user_from_id, user_to_id) 唯一约束：Django 版的 get_or_create 在并发下可能插入重复关注，数据库约束能兜底。

People 页面与关注按钮

PeopleController 提供用户列表、用户详情和关注接口。关注接口和上一章的点赞接口是同一个套路（POST + JSON + 请求头里的 CSRF 令牌）：

/** 固定路径 /follow/ 比 /{username}/ 更具体，Spring 会优先匹配它 */
@PostMapping("/follow/")
@ResponseBody
public Map<String, String> follow(@AuthenticationPrincipal CurrentUser me,
                                  @RequestParam(required = false) Long id,
                                  @RequestParam(required = false) String action) {
    if (id != null && action != null && follows.follow(me.id(), id, "follow".equals(action))) {
        return Map.of("status", "ok");
    }
    return Map.of("status", "error");
}

// FollowService
public boolean follow(Long meId, Long targetId, boolean follow) {
    if (meId.equals(targetId)) {
        return false;                 // 书中允许关注自己，这里拦掉
    }
    return users.findById(targetId).filter(User::isActive).map(target -> {
        if (follow) {
            if (!contacts.existsByUserFromIdAndUserToId(meId, targetId)) {
                contacts.save(new Contact(users.getReferenceById(meId), target));
            }
            actions.create(meId, "is following", target);
        } else {
            contacts.unfollow(meId, targetId);
        }
        return true;
    }).orElse(false);
}
ⓘ URL 匹配顺序

Django 按 urlpatterns 的书写顺序匹配，所以 users/follow/ 必须写在 users/<username>/ 前面，否则用户名为 “follow” 的请求会被错误派发。 Spring MVC 不看书写顺序，而是选择最具体的模式：字面量路径优先于变量。

活动流：GenericForeignKey 的替代

“alice 收藏了一张图片”“bob 关注了 alice”—— 动态的目标可能是图片，也可能是用户。 Django 用 contenttypes 框架的 GenericForeignKey：一列存“是哪个模型”（指向 django_content_type 表），一列存 id。 JPA 没有这个概念，我们用最朴素的办法：一列存类型名，一列存 id。

Django · actions/models.py
class Action(models.Model):
    user = models.ForeignKey(settings.AUTH_USER_MODEL,
        related_name='actions', on_delete=models.CASCADE)
    verb = models.CharField(max_length=255)
    created = models.DateTimeField(auto_now_add=True)
    target_ct = models.ForeignKey(ContentType,
        blank=True, null=True,
        related_name='target_obj',
        on_delete=models.CASCADE)
    target_id = models.PositiveIntegerField(
        null=True, blank=True)
    target = GenericForeignKey('target_ct', 'target_id')
Spring · actions/Action.java（节选）
@Entity
@Table(name = "actions_action", indexes = {

public class Action {
    @ManyToOne(fetch = FetchType.LAZY, optional = false)

create_action：一分钟内不重复记录

Django · actions/utils.py
def create_action(user, verb, target=None):
    now = timezone.now()
    last_minute = now - datetime.timedelta(seconds=60)
    similar_actions = Action.objects.filter(
        user_id=user.id, verb=verb,
        created__gte=last_minute)
    if target:
        target_ct = ContentType.objects.get_for_model(target)
        similar_actions = similar_actions.filter(
            target_ct=target_ct, target_id=target.id)
    if not similar_actions:
        action = Action(user=user, verb=verb, target=target)
        action.save()
        return True
    return False
Spring · ActionService / ActionRepository
public boolean create(Long userId, String verb, ActionTarget target) {
    OffsetDateTime lastMinute = OffsetDateTime.now(clock)
            .minus(Duration.ofSeconds(60));
    String type = target == null ? null : target.targetType();
    Long targetId = target == null ? null : target.getId();
    if (actions.existsSimilar(userId, verb, type, targetId, lastMinute)) {
        return false;
    }
    actions.save(new Action(users.getReferenceById(userId), verb, target));
    return true;
}

⚠ “类型 + id”没有外键约束

这是泛型关系的通病，Django 的 GenericForeignKey 也一样：数据库不知道 target_id 指向哪张表，目标被删除时不会级联，动态里会留下悬空引用。 代码里用 containsKey 跳过找不到的目标；更完整的做法是在删除图片时同时删除相关动态，或者定期清理。

信号 → 应用事件

这一章给 Image 加了一个冗余字段 total_likes，让“按热度排序”不必每次 COUNT 中间表。 Django 版用 m2m_changed 信号维护它：每当 users_like 变化，Django 自动发出信号，接收函数重新计数。

Django · images/signals.py + apps.py
@receiver(m2m_changed, sender=Image.users_like.through)
def users_like_changed(sender, instance, **kwargs):
    instance.total_likes = instance.users_like.count()
    instance.save()

# apps.py —— 必须在 ready() 里导入，接收者才会注册
class ImagesConfig(AppConfig):
    def ready(self):
        import images.signals
Spring · 事件 + 监听器
public record ImageLikesChangedEvent(Long imageId) { }

// 发布方：ImageService.like()
events.publishEvent(new ImageLikesChangedEvent(imageId));

// 监听方：只要是个 Bean 就会被自动注册
@Component
public class ImageLikesListener {

    @EventListener
    public void onLikesChanged(ImageLikesChangedEvent event) {
        images.findById(event.imageId()).ifPresent(image ->
            image.setTotalLikes(image.getUsersLike().size()));
    }

Django 信号Spring 应用事件
内置信号由框架自动发出（post_save、m2m_changed…）业务事件要自己 publishEvent；框架也有内置事件（登录成功、上下文启动…）
@receiver(signal, sender=...)@EventListener，按事件类型分派

🔎 该用哪种监听方式

维护 total_likes 必须和点赞在同一个事务里：要么一起成功，要么一起回滚，所以用普通的 @EventListener。 如果监听器要做的是发邮件、推消息这类“外部副作用”，就应该用 @TransactionalEventListener(phase = AFTER_COMMIT)： 否则事务回滚了，邮件却已经发出去了。Django 里对应的是把副作用放进 transaction.on_commit()。

ⓘ 显式发布 vs 自动信号

Django 的 m2m_changed 在任何地方修改 users_like 都会触发（包括 admin、shell）；Spring 版只有经过 ImageService.like() 的修改才会发布事件。 这是“显式优于隐式”的取舍：调用链一目了然，但要保证所有修改都经过 service。书中也提醒过，信号会让代码的执行路径变得难以追踪。

⚠ Actuator 端点必须保护

/actuator/env、/actuator/heapdump 之类的端点可能泄露密钥和数据。本项目默认只暴露 health， dev profile 才多开几个，并且 SecurityConfig 规定 /actuator/**（除 health 外）只有 ROLE_ADMIN 能访问 —— 测试里验证了普通用户访问 /actuator/beans 会得到 403。 Debug Toolbar 靠 INTERNAL_IPS 限制访问，思路相同。

Spring · images/ImageViews.java + ImageService
public long recordView(Long imageId) {
    Long total = redis.opsForValue()
            .increment("image:" + imageId + ":views");    // INCR
    redis.opsForZSet()
            .incrementScore(RANKING_KEY, imageId.toString(), 1);  // ZINCRBY
    return total == null ? 0 : total;
}

public List<Long> topIds(int count) {
    // ZREVRANGE image_ranking 0 9：让 Redis 只返回前 N 个
    Set<String> ids = redis.opsForZSet()
            .reverseRange(RANKING_KEY, 0, count - 1L);
    return ids == null ? List.of()
            : ids.stream().map(Long::valueOf).toList();
}

// ImageService：IN 查询不保证顺序，按排行重新排序
public List<Image> inOrder(List<Long> ids) {
    Map<Long, Image> byId = images.findAllById(ids).stream()
            .collect(toMap(Image::getId, image -> image));
    return ids.stream().filter(byId::containsKey)
            .map(byId::get).toList();
}
💡 书中的一个小浪费

r.zrange('image_ranking', 0, -1, desc=True)[:10] 先把整个有序集合取回 Python 再切片。图片多了以后应该写成 r.zrange('image_ranking', 0, 9, desc=True)，让 Redis 只返回前 10 个 —— Spring 版就是这么做的。

ⓘ Redis 不参与数据库事务

测试类上的 @Transactional 只会回滚数据库，Redis 里的计数会留下来，所以每个测试开始前执行一次 FLUSHDB。同理，业务代码里“写库 + 写 Redis”也不是原子的：事务回滚时 Redis 不会跟着回滚。浏览计数这种允许误差的数据无所谓，重要数据要小心。

差异点评

🔍 第 7 章 Spring 版点评 springboot/Chapter07

做得好 活动流的查询次数固定

和 Django 的 select_related + prefetch_related 一样，查询次数不随动态数量增长；而且全部在 service 里完成，模板渲染时没有任何隐藏的 SQL。

做得好 关注关系有唯一约束，不能关注自己

修正了原书的两个小问题。

注意 事件只在经过 service 时发布

如果以后有别的代码直接修改 usersLike，total_likes 就会不准。可以把点赞逻辑收进 Image 实体的方法里（image.likeBy(user)），由实体注册领域事件（Spring Data 的 @DomainEvents），保证“改了就一定发事件”。

注意 total_likes 在并发点赞时可能不准

两个事务同时点赞，各自读到的集合大小都没包含对方。Django 版的信号有同样的问题。可以改用 update Image i set i.totalLikes = (select count(...)) where i.id = :id 一条 SQL 计算，或者在查询时实时统计。

补充知识 为什么不用 Hibernate 的 @Any

Hibernate 有 @Any 注解可以映射“多态关联”，写法更接近 GenericForeignKey。但它是 Hibernate 专有特性、查询和预取都不方便。“类型 + id”两列 + 手动批量加载更直观，也更容易迁移。

小结

  • 带额外字段的多对多 → 中间实体 + 两个 @ManyToOne；再加唯一约束。
  • GenericForeignKey → 类型名 + id 两列；读取时按类型分组批量加载。
  • 信号 → publishEvent + @EventListener；副作用放到 @TransactionalEventListener(AFTER_COMMIT)。
  • Debug Toolbar → SQL 日志 + Hibernate 统计 + Actuator 端点（一定要保护）。
  • Redis → StringRedisTemplate 的 opsForValue()、opsForZSet()；开发用 compose，测试用 Testcontainers。
