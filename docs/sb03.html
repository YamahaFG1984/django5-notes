Spring Boot 版 · 第 3 章 · 项目一：博客

扩展博客

博客项目的最后一章。Django 版在这里接入了 django-taggit、自定义模板标签、sitemap 和 syndication 框架，并把数据库换成 PostgreSQL 做全文搜索。 Spring 版做同样的事，但几乎每一样都要换一个思路：标签自己建模，模板标签变成“方言 + 片段”，sitemap 和 RSS 直接输出 XML， 搜索用原生 SQL 调 PostgreSQL 的函数。另外，从这一章起测试会用 Testcontainers 启动一个真正的 PostgreSQL。

本章目标

  • 用 Docker Compose + spring-boot-docker-compose 在开发时自动启动 PostgreSQL
  • 用 @ManyToMany 实现标签，理解它和 django-taggit“泛型关系”的区别
  • 在关闭 open-in-view 的前提下，用 service 层 + 批量抓取实现 prefetch_related
  • 用 JPQL 的 group by + count 写出“相似文章”推荐
  • 把 simple_tag、inclusion_tag、自定义过滤器翻译成 Thymeleaf 方言和片段
  • 安全地渲染 Markdown，并实现 HTML 感知的截断
  • 生成 sitemap.xml 和 RSS；用原生 SQL 做 trigram 模糊搜索
  • 用 Testcontainers 写跑在真实数据库上的集成测试

对应的 Django 讲解见 Django 版第 3 章；本章代码在 springboot/Chapter03/。

💡 用命名卷，别用 ./data/db

原书把数据挂载到项目目录下的 ./data/db。容器里的 postgres 进程以另一个用户身份写文件，宿主机上会留下一堆删不掉的 root 属主文件。用命名卷 pgdata 可以避免这个问题，docker compose down -v 就能清干净。

ⓘ 迁移脚本不用改

第 1、2 章的 SQL 用的都是标准语法（GENERATED BY DEFAULT AS IDENTITY、TIMESTAMP WITH TIME ZONE），H2 和 PostgreSQL 都支持，所以换库时 V1–V3 原样保留。 至于数据：Django 用 dumpdata/loaddata 在两个库之间搬数据，Java 这边没有通用命令，一般用数据库自带的导出工具或写一次性脚本。

标签：自己建模的多对多

django-taggit 是一个“可复用应用”：装上它，给模型加一行 tags = TaggableManager()，就能给任何模型打标签。 它内部用 GenericForeignKey（content_type + object_id）让一张 TaggedItem 表指向任意模型。 Java 生态里没有这样即插即用的库，好在需求很简单：一张标签表 + 一张中间表。 

@Entity
@Table(name = "blog_tag")
public class Tag {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true, length = 100)
    private String name;

    @Column(nullable = false, unique = true, length = 100)
    private String slug;

    public Tag(String name) {
        this.name = name;
        this.slug = Slugs.slugify(name);     // 和 taggit 一样自动生成 slug
    }
}

// Post.java
@ManyToMany
@JoinTable(name = "blog_post_tags",
        joinColumns = @JoinColumn(name = "post_id"),
        inverseJoinColumns = @JoinColumn(name = "tag_id"))
@OrderBy("name")
private Set<Tag> tags = new LinkedHashSet<>();

CREATE TABLE blog_tag (
    id    BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name  VARCHAR(100) NOT NULL UNIQUE,
    slug  VARCHAR(100) NOT NULL UNIQUE
);

CREATE TABLE blog_post_tags (
    post_id  BIGINT NOT NULL REFERENCES blog_post (id) ON DELETE CASCADE,

⚠ 多对多集合用 Set，不要用 List

Hibernate 对 List 类型的多对多（“bag”）处理得很粗暴：改动一个元素时会先删掉该文章的全部中间表记录再逐条插回。 用 Set 则只增删变化的那一行。LinkedHashSet + @OrderBy("name") 让标签按名字有序。

列表里每篇文章都要显示它的标签。第 1 章我们关掉了 open-in-view，模板渲染时数据库会话已经关闭， 直接在模板里访问 post.tags 会抛 LazyInitializationException。 解决办法是引入一个 service 层：在同一个事务里查出分页数据并把标签初始化好。 

@Service
@Transactional(readOnly = true)
public class PostService {

    public Page<Post> publishedPage(Tag tag, int pageNumber) {
        Page<Post> page = fetch(tag, pageNumber);
        if (page.getContent().isEmpty() && page.getTotalPages() > 0) {
            page = fetch(tag, page.getTotalPages());
        }
        page.forEach(post -> Hibernate.initialize(post.getTags()));   // 触发加载
        return page;
    }
    ...
}

单看代码，forEach 里逐篇初始化好像又是 N+1。关键在配置里的这一行：

spring.jpa.properties.hibernate.default_batch_fetch_size: 50

它让 Hibernate 在加载第一篇文章的标签时，顺便把当前会话里其他文章的标签一起加载： ... WHERE post_id IN (?, ?, ?)。一页 3 篇文章，总共只有“文章 1 条 + count 1 条 + 标签 1 条”三条 SQL， 和 Django 的 prefetch_related('tags') 生成的查询几乎一样。

🔎 为什么不直接 join fetch 标签

对“分页 + 集合”的查询做 join fetch，一篇文章有 3 个标签就会变成 3 行，LIMIT 3 就不再是“3 篇文章”了。 Hibernate 发现这种情况会放弃在 SQL 里分页，改为把所有结果读进内存再截取，并打出 HHH90003004 警告 —— 数据一多就是灾难。 所以一对一/多对一用 @EntityGraph 或 join fetch，集合用批量抓取，这和 Django 里“外键用 select_related、多对多用 prefetch_related”的分工一模一样。

  • Django 分两步（先取标签 id，再查文章）；JPQL 用子查询一步完成。
  • group by p 按整个实体分组，Hibernate 会展开成按主键分组；PostgreSQL 允许在按主键分组时选出该表的其他列。
  • Limit（Spring Data 3.2+）是只取前 N 条的轻量写法，不会像 Pageable 那样额外发 count 查询。它对应 QuerySet 的切片 [:4]。

@Component
public class BlogTags {

    private final PostRepository posts;
    private final MarkdownRenderer markdownRenderer;

    /** @register.simple_tag def total_posts() */
    public long totalPosts() {
        return posts.countByStatus(PostStatus.PUBLISHED);
    }

    /** inclusion_tag 的“数据”部分；HTML 部分是一个片段 */
    public List<Post> latestPosts(int count) {
        return posts.findByStatusOrderByPublishDesc(PostStatus.PUBLISHED, Limit.of(count));
    }

    /** get_most_commented_posts */
    public List<Post> mostCommentedPosts(int count) {
        return posts.findMostCommented(PostStatus.PUBLISHED, Limit.of(count));
    }

    /** @register.filter(name='markdown') */
    public String markdown(String text) {
        return markdownRenderer.render(text);
    }
}

⚠ 模板里查数据库：两边都要小心

侧边栏在每个页面都会渲染，于是每次请求都多了 3 条 SQL（总数、最新、评论最多）。Django 和 Spring 在这点上完全一样。 流量大时应该缓存这些结果（第 14 章讲缓存），或者在控制器里统一准备好数据（第 8 章的 @ControllerAdvice）。

Markdown 与 HTML 截断

Python 用 markdown 包，Java 这边选 CommonMark 规范的参考实现之一 commonmark-java：

@Component
public class MarkdownRenderer {

    private final Parser parser = Parser.builder().build();
    private final HtmlRenderer renderer = HtmlRenderer.builder()
            .escapeHtml(true)      // 正文里的原始 HTML 一律转义
            .sanitizeUrls(true)    // 过滤 javascript: 这类危险链接
            .build();

    public String render(String markdown) {
        return markdown == null ? "" : renderer.render(parser.parse(markdown));
    }
}
⚠ mark_safe(markdown.markdown(text)) 的隐患

Python 的 markdown 默认会原样保留正文里的 HTML。书中直接 mark_safe，意味着作者在文章里写一段 <script> 就会在读者浏览器里执行。 对只有自己写文章的博客问题不大，但多作者平台就是存储型 XSS。Spring 版在渲染器上打开 escapeHtml 和 sanitizeUrls，单元测试里专门验证了这两点。 如果确实需要允许部分 HTML，应该用白名单清洗（比如 jsoup 的 Safelist），而不是全部放行。

列表页需要 {{ post.body|markdown|truncatewords_html:30 }}：先转成 HTML，再按单词截断，且不能把标签切坏。 我们借助 HTML 解析库 jsoup，按文档顺序遍历节点，数到第 30 个单词后把后面的节点全部删掉： 

public String truncatewordsHtml(String html, int count) {
    Document doc = Jsoup.parseBodyFragment(html);
    doc.outputSettings().prettyPrint(false);

    List<Node> following = new ArrayList<>();
    TextNode[] cutNode = new TextNode[1];
    int[] cutAt = new int[1];
    int[] seen = new int[1];
    doc.body().traverse((node, depth) -> {
        if (cutNode[0] != null) {            // 已经截断：之后遇到的节点都要删
            following.add(node);
            return;
        }
        if (node instanceof TextNode text) {
            Matcher words = WORD.matcher(text.getWholeText());
            while (words.find()) {
                if (++seen[0] == count) {    // 第 count 个单词在这个文本节点里
                    cutNode[0] = text;
                    cutAt[0] = words.end();
                    return;
                }
            }
        }
    });
    ...   // 如果后面还有单词：截断文本、补 " …"、删除后续节点
    return doc.body().html();
}

String html = "<p>one <strong>two three</strong> four</p><p>five six</p>";
assertThat(filters.truncatewordsHtml(html, 2)).isEqualTo("<p>one <strong>two …</strong></p>");
assertThat(filters.truncatewordsHtml(html, 6)).isEqualTo(html);   // 恰好 6 个单词，不加省略号

这类纯函数用普通 JUnit 测试即可，不需要启动 Spring，相当于 Django 的 SimpleTestCase，几毫秒就跑完。

Sitemap 与 RSS

sitemap.xml

Django 有现成的 sitemap 框架：写一个 Sitemap 子类，声明 items()、lastmod()、changefreq、priority 就行。Spring 没有对应物，但 sitemap 格式很简单，控制器直接拼出 XML 即可：

@RestController                       // 返回值直接写进响应体，而不是当作视图名
public class SitemapController {

    @GetMapping(value = "/sitemap.xml", produces = MediaType.APPLICATION_XML_VALUE)
    public String sitemap() {
        String baseUrl = ServletUriComponentsBuilder.fromCurrentContextPath().toUriString();
        StringBuilder xml = new StringBuilder("""
                <?xml version="1.0" encoding="UTF-8"?>
                <urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
                """);
        for (Post post : posts.findByStatusOrderByUpdatedDesc(PostStatus.PUBLISHED)) {
            String lastmod = post.getUpdated().withOffsetSameInstant(ZoneOffset.UTC)
                    .format(DateTimeFormatter.ISO_LOCAL_DATE);
            url(xml, baseUrl + post.getAbsoluteUrl(), lastmod, "weekly", "0.9");
        }
        for (Tag tag : tags.findAll()) {                       // 仓库 prompts/task.md 里的扩展需求
            url(xml, baseUrl + "/blog/tag/" + tag.getSlug() + "/", null, "weekly", "0.6");
        }
        return xml.append("</urlset>\n").toString();
    }
}
ⓘ 域名从哪来

Django 的 sitemap 使用 Sites 框架里 SITE_ID 对应的域名 —— 默认是 example.com，很多人上线后才发现 sitemap 里全是 example.com。 Spring 版直接用当前请求的协议和主机名。部署在反向代理后面时，要让应用信任代理传来的 X-Forwarded-* 头（server.forward-headers-strategy，第 17 章会配置），否则会生成内网地址。

Django 的 Feed 是“声明式”的：你填钩子方法，框架负责组装。ROME 是“命令式”的：你自己构造对象树，再交给它序列化。换成 Atom 只需要把 feedType 改成 atom_1.0。

                         @RequestParam(required = false) String query, Model model) {
    if (query == null) {
        // 首次打开页面：换成一个新的空表单，原来的“必填”校验错误会随之丢弃
        model.addAttribute("form", new SearchForm());
    } else if (!errors.hasErrors()) {
        model.addAttribute("query", form.getQuery());
        model.addAttribute("results", posts.searchByTrigram(form.getQuery()));
    }
    return "blog/post/search";
}

对应 Django 视图里的 if 'query' in request.GET:：只有提交过查询才校验，第一次打开页面不显示“必填”错误。

扩展：书中其他搜索写法在 Spring 里怎么做

Django 的这些类最终都是在生成 PostgreSQL 的全文检索 SQL。在 Spring 里直接写出这些 SQL 即可（仓库代码没有包含，可作为练习）：

DjangoPostgreSQL SQL
SearchVector('title', 'body')to_tsvector('english', title || ' ' || body)
SearchQuery(query)plainto_tsquery('english', :q) 或 websearch_to_tsquery
filter(search=query)WHERE vector @@ query
SearchRank(vector, query)ts_rank(vector, query)
SearchVector('title', weight='A')setweight(to_tsvector('english', title), 'A')
-- 按权重排序的全文检索：标题权重 A，正文权重 B
SELECT p.* FROM blog_post p,
       websearch_to_tsquery('english', :q) AS query
WHERE p.status = 'PB'
  AND (setweight(to_tsvector('english', p.title), 'A') ||
       setweight(to_tsvector('english', p.body),  'B')) @@ query
ORDER BY ts_rank(setweight(to_tsvector('english', p.title), 'A') ||
                 setweight(to_tsvector('english', p.body),  'B'), query) DESC;
💡 数据多了记得建索引

上面的写法每次都要对全表计算 to_tsvector。数据量大时，可以加一个生成列存放向量并建 GIN 索引；trigram 搜索也可以建 gin (title gin_trgm_ops) 索引。这一点 Django 和 Spring 完全相同。

测试：Testcontainers

trigram 搜索、group by p 这些都依赖 PostgreSQL 的行为，用 H2 测不出问题。从本章起，测试通过 Testcontainers 在 Docker 里启动一个一次性的 PostgreSQL：

@TestConfiguration(proxyBeanMethods = false)
public class TestcontainersConfiguration {

    @Bean
    @ServiceConnection            // 自动把容器地址、账号填进 spring.datasource.*
    PostgreSQLContainer postgres() {
        return new PostgreSQLContainer("postgres:16");
    }
}

// 测试类上：
@SpringBootTest
@AutoConfigureMockMvc
@Import(TestcontainersConfiguration.class)
@Transactional
class BlogFeaturesTests { ... }

Django 的测试运行器会自动创建一个 test_ 前缀的测试库；Testcontainers 更进一步，连数据库服务器都是临时的，CI 机器上只要有 Docker 就能跑。

⚠ @Transactional 测试的一个坑：一级缓存

测试方法和 @BeforeEach 在同一个事务、同一个持久化上下文里。准备数据时 save 过的对象会被缓存， 后面“请求”里查询同一篇文章时，Hibernate 直接返回缓存里的那个对象 —— 于是 @OrderBy("name") 没生效，标签顺序还是插入顺序，测试失败。 解决办法是在准备数据的最后 entityManager.flush(); entityManager.clear();，让后续查询真正从数据库读。

断言方面，侧边栏也会出现文章标题，用 containsString 容易误判。测试里用 jsoup 按 CSS 选择器取出特定区域再断言：

var page = mvc.perform(get("/blog/tag/jazz/"));
assertThat(texts(page, "#content h2 > a"))
        .containsExactly("Gypsy jazz today", "Who was Django Reinhardt?");
assertThat(texts(page, "#content p.tags").getFirst()).isEqualTo("Tags: guitar, jazz, music");

差异点评

🔍 第 3 章 Spring 版点评 springboot/Chapter03

做得好 测试跑在和生产相同的数据库上

Testcontainers + @ServiceConnection 几乎零配置。数据库专有的 SQL（trigram、group by 实体）都被测试覆盖到了。

做得好 Markdown 默认安全

修正了 Django 版 mark_safe(markdown.markdown(...)) 的 XSS 隐患，并用单元测试锁定行为。

做得好 集合预取不再“碰运气”

关闭 open-in-view 之后，标签必须在 service 的事务里初始化；配合批量抓取，一页文章的标签只需一条 SQL。

注意 标签自己实现，功能比 taggit 少

没有“给任意模型打标签”的能力，也没有 taggit 的标签云、相似对象等辅助 API。对单个博客来说够用；如果多个实体都要打标签，要么各建一张中间表，要么引入“目标类型 + 目标 id”的设计（第 7 章的活动流会遇到同样的问题）。

注意 侧边栏的三条查询每次请求都会执行

和 Django 版一样。第 14 章引入 Spring Cache 后可以用 @Cacheable 缓存 BlogTags 的结果。

补充知识 为什么搜索用 GET

搜索不修改数据，而且结果页应当可以收藏、分享、被浏览器后退 —— 所以用 GET，查询词放在 URL 里。这一点两个框架的书里都强调过，第 2 章的 #querystring 也正是为这种带参数的页面准备的。

小结

  • 开发时用 compose.yaml + spring-boot-docker-compose 自动管理 PostgreSQL；测试用 Testcontainers。
  • 标签用 @ManyToMany + Set，没有 taggit 时 get-or-create 等逻辑要自己写。
  • 多对一用 @EntityGraph，集合用 default_batch_fetch_size，两者合起来就是 select_related + prefetch_related。
  • JPQL 支持子查询、group by、count；Limit 对应切片。
  • 模板标签 → 表达式对象方法；inclusion tag → 方法 + 片段；过滤器 → 方法。
  • Markdown 渲染要转义原始 HTML；HTML 截断借助 jsoup。
  • Sitemap 手写 XML，RSS 用 ROME；数据库专有函数用 nativeQuery。
