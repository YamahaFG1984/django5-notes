权限与安全

前面 17 章点评里的“有问题”，将近一半是安全问题：XSS、CSRF、越权访问、SSRF、被滥用的接口。它们分散在各章，看起来各不相同， 其实可以归到几条原则下面。这一篇先把 Django 的权限系统讲完整（第 13 章只用到了一部分），再把全书的安全问题汇总成一张地图， 最后补上书里没讲的几道防线：安全响应头、CSP、限速和依赖审计。

本篇目标

  • 分清认证（你是谁）和授权（你能做什么）
  • 理解 Django 的权限模型：权限、组、has_perm，以及在视图和模板里检查权限
  • 区分模型级权限与对象级权限，用查询过滤或 django-rules 实现“只能改自己的”
  • 用 5.1 的 LoginRequiredMiddleware 把“默认公开”改成“默认需要登录”
  • 把全书的安全问题归类，知道每一类的标准防御
  • 配置安全响应头、CSP、限速、更强的密码哈希和依赖漏洞检查

认证与授权

💡 为什么“不是你的”返回 404 而不是 403

403 等于告诉对方“这个 ID 存在，只是你不能看”。把 owner 条件写进查询（get_object_or_404(Course, pk=pk, owner=request.user)），别人的对象直接查不到，返回 404，既简单又不泄露信息。

书中第 13 章是在 Admin 里手工创建“Instructors”组的。换一台机器、一个新环境就要再点一遍。更好的办法是写一个可重复执行的管理命令，部署时和 migrate 一起运行：

from django.contrib.auth.models import Group, Permission
from django.core.management.base import BaseCommand

INSTRUCTOR_PERMS = [
    'add_course', 'change_course', 'delete_course', 'view_course',
    'add_module', 'change_module', 'delete_module', 'view_module',
    'add_content', 'change_content', 'delete_content',
]


class Command(BaseCommand):
    help = 'Create or update the Instructors group and its permissions'

    def handle(self, *args, **options):
        group, _ = Group.objects.get_or_create(name='Instructors')
        perms = Permission.objects.filter(content_type__app_label='courses',
                                          codename__in=INSTRUCTOR_PERMS)
        group.permissions.set(perms)           # set：多余的去掉，缺的补上，可以反复执行
        self.stdout.write(self.style.SUCCESS(f'Instructors: {perms.count()} permissions'))
ⓘ 为什么不写成数据迁移

模型的权限记录是在 migrate 结束后的 post_migrate 信号里才创建的。在全新的数据库上，数据迁移执行时这些权限还不存在。用管理命令在 migrate 之后执行，就没有这个问题。

对象级权限：“只能改自己的”

has_perm('courses.change_course') 回答的是“能不能改课程”，而真正的问题往往是“能不能改这门课程”。Django 自带的 ModelBackend 只做模型级检查，对象级有两种做法：

import rules


@rules.predicate
def is_course_owner(user, course):
    return course is not None and course.owner_id == user.id


is_instructor = rules.is_group_member('Instructors')

rules.add_perm('courses.change_course', is_instructor & is_course_owner)
rules.add_perm('courses.delete_course', is_instructor & is_course_owner)

INSTALLED_APPS += ['rules.apps.AutodiscoverRulesConfig']    # 自动导入每个应用的 rules.py
AUTHENTICATION_BACKENDS = [
    'rules.permissions.ObjectPermissionBackend',             # 负责对象级检查
    'django.contrib.auth.backends.ModelBackend',
]

# courses/views.py
from rules.contrib.views import PermissionRequiredMixin


class CourseUpdateView(LoginRequiredMixin, PermissionRequiredMixin, UpdateView):
    model = Course
    fields = ['subject', 'title', 'slug', 'overview']
    permission_required = 'courses.change_course'   # 自动用 get_object() 作为检查对象

{% load rules %}
{% has_perm 'courses.change_course' request.user course as can_edit %}
{% if can_edit %}<a href="{% url 'course_edit' course.pk %}">Edit</a>{% endif %}

默认需要登录：LoginRequiredMiddleware

第 13 章的点评里，模块和内容相关的几个视图忘了加 LoginRequiredMixin。“每个视图都记得加”靠的是人，迟早会漏。Django 5.1 提供了反过来的做法：默认所有页面都要登录，公开页面单独标出来。

MIDDLEWARE = [
    # ...
    'django.contrib.auth.middleware.AuthenticationMiddleware',
    'django.contrib.auth.middleware.LoginRequiredMiddleware',    # 必须在 AuthenticationMiddleware 之后
    # ...
]
LOGIN_URL = 'login'

# 公开的函数视图
from django.contrib.auth.decorators import login_not_required

@login_not_required
def course_detail(request, slug): ...

# 公开的类视图：在 urls.py 里包一层
path('', login_not_required(CourseListView.as_view()), name='course_list'),
ⓘ 它只管“登录”，不管“权限”

内置的 LoginView 等认证视图已经标记为公开。中间件只保证“登录了”，模型级和对象级权限仍然要在视图里检查；它也不作用于 Channels 的 WebSocket（第 16 章的消费者要自己检查）。

第 6 章的 SSRF：更安全的下载函数

书中的 ImageCreateForm.save() 直接 requests.get(image_url)：没有超时、不限大小，URL 也可以指向服务器内网（例如云服务器的元数据地址 169.254.169.254）。

import ipaddress
import socket
from urllib.parse import urlsplit

import requests
from django.core.exceptions import ValidationError

MAX_BYTES = 5 * 1024 * 1024


def fetch_image(url):
    parts = urlsplit(url)
    if parts.scheme not in ('http', 'https') or not parts.hostname:
        raise ValidationError('Only http(s) URLs are allowed.')

    port = parts.port or (443 if parts.scheme == 'https' else 80)
    for *_, sockaddr in socket.getaddrinfo(parts.hostname, port):
        if not ipaddress.ip_address(sockaddr[0]).is_global:      # 内网、回环、链路本地一律拒绝
            raise ValidationError('This address is not allowed.')

    with requests.get(url, timeout=5, stream=True, allow_redirects=False) as response:
        response.raise_for_status()
        if not response.headers.get('Content-Type', '').startswith('image/'):
            raise ValidationError('The URL does not point to an image.')
        data = bytearray()
        for chunk in response.iter_content(64 * 1024):
            data.extend(chunk)
            if len(data) > MAX_BYTES:
                raise ValidationError('Image is too large.')
    return bytes(data)
⚠ 还有一个缝隙

先解析域名再请求，两次解析之间 DNS 结果可能被换掉（DNS rebinding）。要求更高的系统会让所有出站请求走一个专门的出站代理，由代理统一拦截内网地址。对学习项目来说，上面的写法已经挡住了绝大多数问题。

安全响应头与 CSP

CSP（内容安全策略）告诉浏览器“这个页面只允许执行来自哪里的脚本”。即使攻击者成功注入了 <script>，浏览器也会拒绝执行。 它是 XSS 的最后一道防线。书中的模板有不少内联脚本（例如 {% block domready %}），所以要用 nonce：服务器每次响应生成一个随机值，只有带着这个值的 <script> 才能执行。 

from csp.constants import NONCE, NONE, SELF

MIDDLEWARE += ['csp.middleware.CSPMiddleware']

CONTENT_SECURITY_POLICY = {
    'DIRECTIVES': {
        'default-src': [SELF],
        'script-src': [SELF, NONCE],                   # 内联脚本必须带 nonce
        'style-src': [SELF],
        'img-src': [SELF, 'data:'],
        'frame-src': ['https://www.youtube.com'],      # 第 12 章嵌入的视频
        'frame-ancestors': [NONE],
        'object-src': [NONE],
    },
}

<script nonce="{{ request.csp_nonce }}">
  document.addEventListener('DOMContentLoaded', (event) => {
    {% block domready %}{% endblock %}
  })
</script>
💡 先观察，再拦截

先用 CONTENT_SECURITY_POLICY_REPORT_ONLY 上线：浏览器只报告违规、不拦截。看一段时间的报告，把合法的来源（CDN、视频、Stripe）都加进白名单，再切换成真正生效的策略。Django 6.0 起内置了 CSP 支持（SECURE_CSP 设置加 ContentSecurityPolicyMiddleware），思路完全相同。

SECURE_HSTS_SECONDS = 60 * 60 * 24 * 365     # 确认 HTTPS 稳定后再设成一年
SECURE_HSTS_INCLUDE_SUBDOMAINS = True
SESSION_COOKIE_SECURE = True
CSRF_COOKIE_SECURE = True

# 更强的密码哈希（先 pip install "django[argon2]"）；旧密码在用户下次登录时自动升级
PASSWORD_HASHERS = [
    'django.contrib.auth.hashers.Argon2PasswordHasher',
    'django.contrib.auth.hashers.PBKDF2PasswordHasher',
]

限速：别让接口被无限调用

场景工具例子
普通视图django-ratelimit@ratelimit(key='ip', rate='10/m', method='POST', block=True)，用在第 10 章的 coupon_apply；超限默认返回 403，可用 RATELIMIT_VIEW 改成 429
DRF 接口内置节流DEFAULT_THROTTLE_CLASSES + DEFAULT_THROTTLE_RATES = {'anon': '100/hour', 'user': '1000/hour'}
登录django-axes连续失败 N 次后锁定账号或 IP
整站兜底反向代理 / CDNNginx 的 limit_req、Cloudflare 规则

其他防线

  • Admin：Two Scoops 建议把 admin/ 改成不容易猜到的路径，给管理员开启两步验证（django-otp、django-allauth 的 MFA），必要时在反向代理上按 IP 限制访问。
  • 依赖漏洞：定期运行 pip-audit，或打开 GitHub 的 Dependabot，第三方包出现已知漏洞时会收到提醒。
  • 错误信息：线上 DEBUG = False；错误报告里用 sensitive_post_parameters 隐藏密码（专题 3）。
  • 最小权限：数据库账号只给应用需要的权限；Celery、Web 进程用非 root 用户运行（专题 7）。

做得好 课程管理视图的三层检查 Chapter13/educa/courses/views.py

OwnerCourseMixin 同时继承 LoginRequiredMixin、PermissionRequiredMixin，并用 OwnerMixin 在查询里过滤 owner：登录、模型级权限、对象归属三关都有。CourseModuleUpdateView 用 get_object_or_404(Course, id=pk, owner=request.user) 也是同样的思路，只是漏了登录检查。

有问题 服务器替用户下载任意 URL Chapter06/bookmarks/images/forms.py:34

requests.get(image_url) 没有超时、没有大小限制，也不检查目标地址；扩展名检查只看 URL 字符串的结尾。改用上文的 fetch_image()。

有问题 排序接口豁免了 CSRF Chapter13/educa/courses/views.py:166

ModuleOrderView 和 ContentOrderView 继承 CsrfExemptMixin，任何网站都能让已登录的讲师在不知情时提交排序请求。去掉豁免，让前端 fetch 带上 X-CSRFToken 头。

建议改进 API 的对象级权限只在详情接口生效 Chapter15/educa/courses/api/permissions.py

IsEnrolled 只实现了 has_object_permission。DRF 只在 get_object() 时调用它，列表接口不会逐个检查。需要“只能看到自己选的课”的列表时，要在 get_queryset() 里按用户过滤。

建议改进 没有任何限速和 CSP

第 2 章的分享邮件、第 10 章的券码、登录表单都可以被无限次调用；全站也没有 CSP。按本篇的做法加上 django-ratelimit 和 django-csp，先用 report-only 模式观察。

小结

  • 认证解决“你是谁”，授权解决“你能做什么”；授权分登录、模型级权限、对象级权限三层。
  • 权限授予组，用户加入组；用管理命令创建组，避免手工在 Admin 里点。
  • 对象级权限：简单时把 owner 条件写进查询，规则多时用 django-rules 集中定义。
  • 5.1 的 LoginRequiredMiddleware 让“忘了加登录保护”不再可能，但权限仍要自己检查。
  • 安全问题大多是“不可信输入被信任了”：转义输出、校验来源、检查归属、限制外连、限制频率，再用安全头和 CSP 兜底。
