Spring Boot 版 · 第 11 章 · 项目三：在线商店

国际化

商店要支持英语和西班牙语：界面文字要翻译，URL 带语言前缀（/es/carro/），商品名称和描述按语言存储， 数字和日期按当地习惯显示，表单校验信息也要翻译。Django 为此提供了 gettext、LocaleMiddleware、i18n_patterns， 书中再加上 Rosetta、django-parler 和 django-localflavor。Spring 有同样坚实的底层（MessageSource、LocaleResolver）， 但“URL 语言前缀”和“模型翻译”需要自己搭 —— 这一章会用到几个很有意思的 Servlet 技巧，也会踩两个很有代表性的坑。

本章目标

  • 用 MessageSource 和 messages_xx.properties 翻译界面，处理参数和复数
  • 理解 LocaleResolver 的作用，自己实现“语言来自 URL 前缀”
  • 用“把语言前缀当作上下文路径”的技巧实现 i18n_patterns，用包装 encodeURL 实现翻译过的 URL
  • 用翻译表实现 django-parler 的模型翻译，并把旧数据迁移过去
  • 按语言格式化金额；写一个自定义 Bean Validation 约束代替 localflavor，并翻译校验信息
  • 理解两个坑：Security 的 DisableEncodeUrlFilter、@EntityGraph 的 FETCH 语义

对应的 Django 讲解见 Django 版第 11 章；本章代码在 springboot/Chapter11/。

  • {0,choice,1#…|1<…} 是 java.text.MessageFormat 的选择格式：数量为 1 用第一段，大于 1 用第二段。它比 gettext 的复数规则简单，对英语、西班牙语足够；俄语、阿拉伯语这类复数形式多的语言，建议用 ICU4J 的 MessageFormat（支持 {0, plural, one{…} few{…} other{…}}）。
  • Spring Boot 自动配置 MessageSource，只需告诉它文件位置：spring.messages.basename=i18n/messages。另设 fallback-to-system-locale: false，避免找不到西语时退到服务器操作系统的语言。
  • MessageFormat 里单引号是转义符，文本里的 ' 要写成 ''（英文的 “don't” 要写成 “don''t”）。

URL 语言前缀：i18n_patterns

LocaleResolver 决定“当前请求用什么语言”。Spring 自带几种：按 Accept-Language 头、按 Cookie、按会话。 但 Django 的 i18n_patterns 是按 URL 前缀，Spring 没有现成实现。我们需要两个部件： 

public class PrefixLocaleResolver implements LocaleResolver {
    @Override
    public Locale resolveLocale(HttpServletRequest request) {
        Object language = request.getAttribute(LocalePrefixFilter.LANGUAGE_ATTRIBUTE);   // 过滤器放进去的
        return Languages.locale(language instanceof String code ? code : Languages.DEFAULT);
    }
}

// I18nConfig：Bean 名字必须是 localeResolver，DispatcherServlet 按名字找
@Bean
LocaleResolver localeResolver() {
    return new PrefixLocaleResolver();
}

核心技巧：把 /es 当作上下文路径

最麻烦的不是“读出前缀”，而是生成链接：模板里有几十个 @{/cart/}、控制器里有几十个 "redirect:/cart/"，难道都要改成带语言的吗？ Servlet 规范里有一个现成的概念：上下文路径（应用部署在 /shop 下时就是 /shop）。 Thymeleaf 的 @{...} 和 Spring 的重定向都会自动在前面加上上下文路径。 那么只要让下游认为“这个请求的上下文路径是 /es”，所有链接就天然带上了语言前缀： 

Matcher matcher = PREFIX.matcher(path);                          // ^/(en|es)(/.*)?$
if (!matcher.matches()) {
    // 没有语言前缀：按 Accept-Language 重定向（≈ LocaleMiddleware）
    String language = preferredLanguage(request);
    response.sendRedirect(contextPath + "/" + language + UrlTranslations.toLocal(language, path) + query);
    return;
}
String language = matcher.group(1);
String canonical = UrlTranslations.toCanonical(language, rest);   // /carro/add/1/ → /cart/add/1/
request.setAttribute(LANGUAGE_ATTRIBUTE, language);
chain.doFilter(new PrefixedRequest(request, contextPath + "/" + language, canonical),
               new TranslatingResponse(response, contextPath + "/" + language, language));

/** 让下游看到：上下文路径 = /es，应用内路径 = /cart/add/1/ */
private static final class PrefixedRequest extends HttpServletRequestWrapper {
    public String getContextPath() { return contextPath; }
    public String getRequestURI()  { return contextPath + pathWithinApplication; }
    public String getServletPath() { return pathWithinApplication; }
    ...
}

翻译过的 URL：包装 encodeURL

Django 版还翻译了 URL 片段：path(_('cart/'), ...)，西语里是 /es/carro/。 进站方向好办：过滤器把 carro 翻译回 cart 再交给控制器。出站方向又用到一个 Servlet 规范： 所有生成的链接都应该经过 response.encodeURL()（它原本是用来在 Cookie 不可用时往 URL 里加 ;jsessionid= 的）。 Thymeleaf 的链接和 Spring 的重定向都遵守这个约定，于是我们包装响应对象，在这里把 /es/cart/ 翻译成 /es/carro/： 

private static final class TranslatingResponse extends HttpServletResponseWrapper {
    @Override
    public String encodeURL(String url) {
        return super.encodeURL(translate(url));          // /es/cart/ → /es/carro/
    }
    @Override
    public String encodeRedirectURL(String url) {
        return super.encodeRedirectURL(translate(url));
    }
}

/** 语言 → (英文片段 → 本地化片段)，≈ .po 里的 msgid "cart/" → msgstr "carro/" */
private static final Map<String, Map<String, String>> TO_LOCAL = Map.of(
        "es", Map.of("cart", "carro", "orders", "pedidos", "create", "crear",
                     "payment", "pago", "process", "procesar", "completed", "completado",
                     "canceled", "cancelado", "coupons", "cupon"));

控制器和模板一行都不用改：@{/orders/create/} 在西语页面上输出 /es/pedidos/crear/。Stripe 的回调地址也调用了 response.encodeURL，西语顾客付款后回到 /es/pago/completado/。

⚠ 坑一：Spring Security 会“吞掉” encodeURL

第一版把这个过滤器放在最前面（比 Security 更早），测试发现表单的 action 始终是 /es/cart/add/1/，没有被翻译。 原因是 Spring Security 默认的 DisableEncodeUrlFilter 会把响应包成“encodeURL 原样返回”，防止 jsessionid 泄露到 URL 里； 它包在我们的包装外面，我们的 encodeURL 根本没被调用。解决办法是把语言过滤器排到 Security 过滤器链之后（order 0 > -100）， 这样我们的包装在最外层：先翻译，再交给它。本项目需要权限控制的只有不带前缀的 /admin/**，所以顺序调整没有副作用。

模型翻译：django-parler → 翻译表

商品名称、描述、slug 也要翻译。django-parler 的做法是为每个可翻译模型生成一张 xxx_translation 表。Spring 版手工建出同样的结构：

Django · shop/models.py
class Product(TranslatableModel):
    translations = TranslatedFields(
        name=models.CharField(max_length=200),
        slug=models.SlugField(max_length=200),
        description=models.TextField(blank=True),
    )
    category = models.ForeignKey(...)
    image = ...
    price = ...
Spring · shop/Product.java（节选）
@OneToMany(mappedBy = "master", cascade = CascadeType.ALL,
           orphanRemoval = true, fetch = FetchType.EAGER)
@MapKey(name = "languageCode")        // Map<语言, 译文>
@Fetch(FetchMode.SUBSELECT)
private Map<String, ProductTranslation> translations = new HashMap<>();

/** 当前语言的译文，没有就回退到英文 */
private ProductTranslation current() {
    ProductTranslation t = translations.get(Languages.current());
    return t != null ? t : translations.get(Languages.DEFAULT);
}

public String getName() {
    ProductTranslation t = current();
    return t == null ? "" : t.getName();
}

getName() 返回当前语言的名字 —— 和 parler 一样，实体依赖一个线程绑定的“当前语言”（LocaleContextHolder ≈ translation.get_language()）。 模板照旧写 ${product.name}，在 /es/ 下自动显示 “Té verde”；没有西语译文的 “Tea powder” 回退显示英文（parler 的 fallback: 'en'）。

             type = EntityGraph.EntityGraphType.LOAD)

    select p from Product p join p.translations t
    where p.id = :id and p.available = true
      and t.languageCode = :language and t.slug = :slug

Optional<Product> findAvailableByTranslatedSlug(
        @Param("id") Long id, @Param("language") String language,
        @Param("slug") String slug);

slug 按语言匹配：/es/1/te-verde/ 能找到，/en/1/te-verde/ 是 404。按名字排序则只能在取出后于内存中进行（名字在译文表里、随语言变化）—— 书中也因此把模型上的 ordering = ['name'] 注释掉了。

⚠ 坑二：@EntityGraph 默认会把 EAGER 变成 LAZY

这一章最有教育意义的 bug：所有测试都通过了，真正启动应用打开西语商品页却报 LazyInitializationException: Cannot lazily initialize collection Product.translations。 有两层原因：

  1. Spring Data 的 @EntityGraph 默认类型是 FETCH：图里列出的属性立即加载，没列出的一律按 LAZY 处理 —— 包括映射上写了 EAGER 的 translations。改成 type = LOAD（没列出的沿用映射设置）就好了。
  2. 测试为什么没发现？因为测试类上有 @Transactional，整个测试方法在一个事务里，Hibernate 会话一直开着，模板渲染时的懒加载“碰巧”成功了 —— 和 open-in-view 掩盖问题的方式一模一样。

修复后，I18nTests 特意不加 @Transactional（自己清理数据），并补了一个完整的“西语下单 → 支付页”测试。 另外，EAGER 集合配合 @BatchSize 在 Hibernate 7 里也不会立即初始化，这里用的是 @Fetch(FetchMode.SUBSELECT)。

后台编辑译文

parler 的 TranslatableAdmin 为每种语言显示一个标签页。手写后台里，表单对象用 Map<String, TranslationFields>，输入框名字形如 translations[es].name，Spring 的数据绑定能直接填进 Map：

<fieldset th:each="language : ${languages}" th:with="code=${language.code}">
  <legend th:text="${language.nameLocal}">English</legend>
  <input type="text" th:id="|name-${code}|" th:field="*{translations[__${code}__].name}">
  <input type="text" th:id="|slug-${code}|" th:field="*{translations[__${code}__].slug}">
  <textarea th:field="*{translations[__${code}__].description}"></textarea>
</fieldset>

校验规则：英文必填；西语要么全空（使用回退），要么名字和 slug 都填。错误用 errors.rejectValue("translations[es].slug", ...) 挂到具体的输入框上。

本地化格式

Django 5 默认开启本地化：模板里的数字和日期会按当前语言格式化，西语里 45.50 显示为 45,50。Thymeleaf 也有 #numbers、#temporals，它们会使用当前 Locale；这里再写一个小工具统一金额格式：

public String money(BigDecimal amount) {
    NumberFormat format = NumberFormat.getNumberInstance(locale);   // es → 1.234,50
    format.setMinimumFractionDigits(2);
    format.setMaximumFractionDigits(2);
    return "$" + format.format(amount);
}

// 方言：每次渲染用模板上下文的 Locale 构造
public Object buildObject(IExpressionContext context, String name) {
    return "fmt".equals(name) ? new Formats(context.getLocale()) : filters;
}

模板里把第 8–10 章的 ${'$' + product.price} 统一换成 ${#fmt.money(product.price)}。日期用 #temporals.format(order.created, 'MMM dd, yyyy') 时，月份名称也会自动变成西语。

localflavor → 自定义校验约束

书中用 django-localflavor 的 USZipCodeField 校验邮编。Bean Validation 里，自定义约束 = 一个注解 + 一个校验器：

@Constraint(validatedBy = UsZipCodeValidator.class)
@Target({ElementType.FIELD, ElementType.PARAMETER})
@Retention(RetentionPolicy.RUNTIME)
public @interface UsZipCode {
    String message() default "{validation.us-zip-code}";   // 花括号：到消息文件里找这个键
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

public class UsZipCodeValidator implements ConstraintValidator<UsZipCode, String> {
    private static final Pattern ZIP = Pattern.compile("^\\d{5}(-\\d{4})?$");

    public boolean isValid(String value, ConstraintValidatorContext context) {
        return value == null || value.isBlank() || ZIP.matcher(value.strip()).matches();
    }
}

// OrderCreateForm
@NotBlank @Size(max = 20) @UsZipCode
private String postalCode;
  • Spring Boot 让 Bean Validation 从 MessageSource 解析 {...} 消息，所以自定义消息写在 messages*.properties 里就能按语言翻译。
  • 内置约束的默认消息（“must not be blank”）Hibernate Validator 自带了多种语言，西语页面上自动显示 “no debe estar vacío”。第 2 章点评里提到的“英文默认消息”问题，在这里一并解决。
  • 表单标签也要翻译：字段片段的第二个参数改为 #{order.postal-code}（≈ models.CharField(_('postal code'), ...)）。

差异点评

🔍 第 11 章 Spring 版点评 springboot/Chapter11

做得好 控制器和模板对语言“无感”

借助“上下文路径”和 encodeURL 两个 Servlet 标准机制，现有的几十个链接和重定向一行没改就带上了语言前缀和翻译过的路径。

做得好 用真实行为测试

发现 @Transactional 测试掩盖了懒加载问题后，改为无事务测试并补上关键流程。这个教训适用于所有 Spring + JPA 项目。

注意 没有 makemessages

Django 能从代码里自动提取待翻译文本并标出过期条目；Spring 的 properties 全靠手工维护：西语文件漏了某个键时，会悄悄回退到 messages.properties 里的英文，很难发现；两个文件都没有的键则显示成 ??key_es??。可以写一个测试比较两份 properties 的键集合，保证它们一致。

注意 规范路径在任何语言下都能访问

过滤器只翻译“认识的”片段，所以 /es/cart/ 也能访问（Django 版会返回 404）。对 SEO 来说最好把它 301 重定向到 /es/carro/，避免重复内容。

补充知识 为什么不在 URL 里用 {lang} 变量

也可以把所有映射改成 @GetMapping("/{lang}/cart/")，但每个控制器方法都要多一个参数，所有链接都要手动带上语言 —— 这正是 i18n_patterns 替你省掉的工作。过滤器方案把横切关注点集中到了一处。

小结

  • 界面翻译：MessageSource + messages_xx.properties，模板里 #{key(参数)}，复数用 choice 格式。
  • 语言来自 URL 前缀：自定义 LocaleResolver + 过滤器；把前缀当作上下文路径，包装 encodeURL 翻译出站链接。
  • 模型翻译：主表 + 译文表，Map<语言, 译文>，按当前语言取值并回退；用 SQL 迁移旧数据。
  • @EntityGraph 的默认 FETCH 类型会让未列出的属性变成 LAZY；需要保留 EAGER 时用 LOAD。
  • 本地化格式用当前 Locale；自定义约束的消息也能翻译。

动手练习

  1. 写一个测试，读取 messages.properties 和 messages_es.properties，断言两者的键集合完全相同。
  2. 把 /es/cart/ 这类“未翻译的规范路径”改为 301 重定向到翻译后的地址。
  3. 加入第三种语言（比如德语），需要改动哪些地方？尽量让它只需要新增文件。
  4. 让语言选择器链接到“当前页面的另一种语言版本”，而不是首页（提示：商品详情页的 slug 也要换成另一种语言的）。
