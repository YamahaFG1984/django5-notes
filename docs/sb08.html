Spring Boot 版 · 第 8 章 · 项目三：在线商店

构建在线商店

第三个项目是一家网店：商品目录、存在会话里的购物车、下单，以及下单后异步发送确认邮件。 Django 版用 request.session 做购物车、用上下文处理器让每个页面都能显示购物车、用 Celery + RabbitMQ 跑后台任务。 Spring 版对应的是 @SessionScope Bean、@ControllerAdvice 和 Spring AMQP —— 还会遇到一个 Django 版不太明显的问题： 消息应该在事务提交之后再发。

本章目标

  • 用 BigDecimal 建模价格，理解“最具体优先”的 URL 匹配
  • 用 @SessionScope Bean 实现会话购物车，理解作用域代理
  • 用 @ControllerAdvice + @ModelAttribute 实现上下文处理器
  • 把订单和订单项建模成一个聚合（级联保存）
  • 用 Spring AMQP + RabbitMQ 实现 Celery 式的异步任务，并用 @TransactionalEventListener 保证时机正确
  • 在手写后台里实现 list_editable：把一张表格绑定到对象列表
  • 用 Docker Compose 管理 RabbitMQ 和 Mailpit，用 profile 加载示例数据

对应的 Django 讲解见 Django 版第 8 章；本章代码在 springboot/Chapter08/（Maven 项目名 myshop）。

⚠ 钱永远用 BigDecimal

Python 的 DecimalField 返回 Decimal；Java 里对应 BigDecimal。千万不要用 double：0.1 + 0.2 == 0.30000000000000004。 还要注意 BigDecimal 的比较：new BigDecimal("30.0").equals(new BigDecimal("30.00")) 是 false（精度不同），比较数值要用 compareTo，测试里用 AssertJ 的 isEqualByComparingTo。

URL：最具体优先

商店挂在网站根路径：/、/{分类}/、/{id}/{slug}/。书中特意提醒：shop.urls 必须放在主 urls.py 的最后，否则 '<slug:category_slug>/' 会把 cart/、orders/ 也当成分类吞掉。

@GetMapping("/{categorySlug}/")
public String productListByCategory(@PathVariable String categorySlug, Model model) { ... }

@GetMapping("/{id:\\d+}/{slug}/")          // {变量:正则}，≈ <int:id>
public String productDetail(@PathVariable Long id, @PathVariable String slug, Model model) { ... }

Spring MVC 不按书写顺序匹配，而是在所有候选里选最具体的：字面量路径 /cart/ 优先于变量 /{categorySlug}/。 所以控制器写在哪里、先注册谁都无所谓。{id:\d+} 限定 id 只能是数字，作用和 Django 的 <int:id> 转换器一样。

会话购物车

购物车不需要登录：匿名用户也有会话。Django 版每次请求都 Cart(request)，从 request.session['cart'] 里取一个字典。Spring 有更“声明式”的写法：

Django · cart/cart.py（节选）
class Cart:
    def __init__(self, request):
        self.session = request.session
        cart = self.session.get(settings.CART_SESSION_ID)
        if not cart:
            cart = self.session[settings.CART_SESSION_ID] = {}
        self.cart = cart

    def add(self, product, quantity=1,
            override_quantity=False):
        product_id = str(product.id)
        if product_id not in self.cart:
            self.cart[product_id] = {
                'quantity': 0,
                'price': str(product.price)}
        if override_quantity:
            self.cart[product_id]['quantity'] = quantity
        else:
            self.cart[product_id]['quantity'] += quantity
        self.save()

    def save(self):
        self.session.modified = True
Spring · cart/Cart.java（节选）
@Component
@SessionScope          // 每个 HTTP 会话一个实例
public class Cart implements Serializable {

    public record Item(int quantity, String price)
            implements Serializable { ... }

    private final Map<Long, Item> items = new LinkedHashMap<>();

    public void add(Product product, int quantity,
                    boolean overrideQuantity) {
        Item current = items.get(product.getId());
        int newQuantity = overrideQuantity || current == null
                ? quantity : current.quantity() + quantity;
        String price = current == null
                ? product.getPrice().toPlainString()
                : current.price();
        items.put(product.getId(), new Item(newQuantity, price));
    }
    // 不需要 session.modified = True
}
  • 作用域代理：CartController 是单例，却能注入一个“每个会话一份”的 Cart。容器注入的是代理对象，每次方法调用时，代理从当前请求的 HttpSession 里取出（或创建）真正的实例。
  • Serializable：会话可能被持久化（重启不丢）或复制到其他节点（集群），里面的对象必须可序列化 —— 和 Django 默认要求会话数据能 JSON 序列化是同一个道理。所以两边都只存“商品 id → 数量和价格字符串”，不存商品对象。
  • 不需要 session.modified = True：Spring 在请求结束时会把会话作用域的 Bean 重新写回会话。
ⓘ 也可以像 Django 一样直接用 HttpSession

控制器方法可以直接声明 HttpSession session 参数，session.getAttribute("cart") 自己管理。第 9 章保存 order_id 就是这么做的。@SessionScope 更适合“有行为的对象”，HttpSession 更适合零散的值。

把 id 变成商品：CartService

Django 的 Cart.__iter__ 在遍历时查询商品。Spring 版把这件事放进 service，一条 IN 查询取回所有商品，得到模板要用的“购物车行”：

public record Line(Product product, int quantity, BigDecimal price) {
    public BigDecimal totalPrice() {
        return price.multiply(BigDecimal.valueOf(quantity));
    }
}

public List<Line> lines() {
    Map<Long, Cart.Item> items = cart.items();
    Map<Long, Product> byId = products.findByIdIn(items.keySet()).stream()
            .collect(Collectors.toMap(Product::getId, Function.identity()));
    return items.entrySet().stream()
            .filter(entry -> byId.containsKey(entry.getKey()))   // 商品已被删除：跳过
            .map(entry -> new Line(byId.get(entry.getKey()), entry.getValue().quantity(), entry.getValue().unitPrice()))
            .toList();
}

表单：数量 + 隐藏的 override

@PostMapping("/add/{productId}/")
public String add(@PathVariable Long productId, @Valid @ModelAttribute CartAddProductForm form, BindingResult errors) {
    Product product = products.findById(productId)
            .filter(Product::isAvailable)   // 书中没有检查：下架商品也能加进购物车
            .orElseThrow(() -> new NotFoundException("No Product matches the given query."));
    if (!errors.hasErrors()) {
        cart.add(product, form.getQuantity(), form.isOverride());
    }
    return "redirect:/cart/";
}

CartAddProductForm 用 @Min(1) @Max(20) 表达 TypedChoiceField(choices=1..20)：Django 的 choices 字段会拒绝列表外的值，Spring 里要用约束注解明确写出来 —— 否则有人手工提交 quantity=-5 就能“退款”。

上下文处理器 → @ControllerAdvice

每个页面顶部都显示“购物车：3 件，$91.50”。Django 用上下文处理器把 cart 放进所有模板的上下文；Spring 用 @ControllerAdvice 里的 @ModelAttribute 方法：

Django
# cart/context_processors.py
def cart(request):
    return {'cart': Cart(request)}

# settings.py
TEMPLATES = [{ ...
    'OPTIONS': {'context_processors': [
        ...
        'cart.context_processors.cart',
    ]},
}]
Spring · cart/CartAdvice.java
@ControllerAdvice   // 对所有控制器生效
public class CartAdvice {

    public record CartSummary(int totalItems,
                              BigDecimal totalPrice) { }

    private final Cart cart;

    @ModelAttribute("cartSummary")   // 每个请求都执行
    public CartSummary cartSummary() {
        return new CartSummary(cart.size(), cart.totalPrice());
    }
}
ⓘ 两者的细微差别

Django 的上下文处理器只在用 RequestContext 渲染模板时执行；@ModelAttribute 方法在每个控制器方法之前执行，哪怕它最后返回的是重定向或 JSON。 所以这里只放计算很便宜的数据（数量和总价都来自会话，不查库）。需要限定范围时可以写 @ControllerAdvice(assignableTypes = ...) 或 basePackages。

@Entity

        items.add(item);
        item.setOrder(this);
    }

@Transactional
public Order create(OrderCreateForm form) {
    Order order = form.toOrder();
    for (CartService.Line line : cartService.lines()) {
        order.addItem(new OrderItem(line.product(),
                line.price(), line.quantity()));
    }
    orders.save(order);   // cascade：订单项一起插入
    cart.clear();
    events.publishEvent(new OrderCreatedEvent(order.getId()));
    return order;
}
  • cascade = CascadeType.ALL：保存订单时自动保存订单项，不必逐个 save。订单项离开订单没有意义，这种“一起创建、一起删除”的对象组合在领域驱动设计里叫聚合。
  • Django 版的多条 INSERT 默认各自提交，中途出错会留下“有订单没订单项”的半成品；Spring 版整个方法在一个事务里。
  • 订单项保存下单时的价格：以后商品调价，历史订单不受影响。测试 checkoutCreatesOrderWithItemsAndClearsCart 专门验证了这一点。
  • 书中允许用空购物车下单（生成一个没有商品的订单），Spring 版在控制器里挡掉了。

🔑 为什么要等事务提交后再发消息

如果在 OrderService.create() 里直接 convertAndSend，消息会在事务提交之前进入队列。 消费者可能比事务更快，去数据库里找订单时发现“不存在”；更糟的是，如果事务最终回滚，确认邮件却已经发出去了。 Django 版没有暴露这个问题，只是因为 Django 默认自动提交（每条 SQL 立即提交）；一旦你把视图包进 transaction.atomic()， 就必须改成 transaction.on_commit(lambda: order_created.delay(order.id)) —— 这正是 @TransactionalEventListener(AFTER_COMMIT) 的对应物。

ⓘ 不用消息队列行不行

Spring 自带更轻量的选择：给方法加 @Async（配合 @EnableAsync），它会在线程池里执行。缺点是任务只存在于内存，应用重启就丢了，也无法由多台机器分担。 对“发确认邮件”这种可以丢、可以重试的任务，@Async 往往就够了；对“扣库存”“对账”这类不能丢的任务，才值得上 RabbitMQ。书中用 Celery 主要是为了演示。

后台：list_editable

Django 的 list_editable = ['price', 'available'] 让管理员在列表页直接改价格和上架状态，一次保存多行。在 Spring 里，这是“把一张表格绑定到对象列表”的问题：

        private boolean available;
        ...
    }
}

💡 复选框的小坑

未勾选的复选框根本不会被提交，服务器无法区分“没勾选”和“没这个字段”。th:field 会额外生成一个隐藏的 _rows[0].available 字段，Spring 看到它就知道“这个复选框存在但没勾选”，于是设为 false。Django 的 CheckboxInput 是靠“字段不在 POST 里就是 False”来处理的。

这种 List<Row> 绑定是第 13 章实现 Django formset 的基础。

差异点评

🔍 第 8 章 Spring 版点评 springboot/Chapter08

做得好 消息在事务提交后才发出

用 @TransactionalEventListener(AFTER_COMMIT) 解决了“消费者比事务快”和“回滚后仍发邮件”两个问题。Django 版若加上事务，也需要 on_commit。

做得好 修补了几个输入校验的漏洞

下架商品不能加入购物车、数量限制在 1–20、空购物车不能下单。Django 版前两项依赖表单的 choices 和视图的 get_object_or_404(Product, id=...)（没有过滤 available）。

注意 会话作用域 Bean 的并发

同一个用户在两个标签页里同时点“加入购物车”，两个请求会并发修改同一个 Cart 实例。LinkedHashMap 不是线程安全的；负载不高时问题不大，严格起见可以把 add 等方法加上 synchronized。Django 的会话也有“后写覆盖先写”的问题。

注意 管理命令要自己退出

这个项目里有 RabbitMQ 监听器线程，以非 Web 模式运行 --createsuperuser 时进程不会自己结束。CreateSuperuserCommand 执行完后调用 SpringApplication.exit() 显式退出 —— 这是在本地验证时发现的。

补充知识 会话存在哪里

默认存在 Tomcat 的内存里，重启就丢、多台机器之间不共享。Django 默认存在数据库里。生产环境可以加 spring-boot-starter-session-data-redis（或 session-jdbc），一行依赖就把会话挪到 Redis，代码不用改。

小结

  • 价格用 BigDecimal，比较用 compareTo；URL 按“最具体优先”匹配。
  • @SessionScope Bean 通过代理访问当前会话的实例；会话里的对象要可序列化，只存 id 和简单值。
  • @ControllerAdvice + @ModelAttribute ≈ 上下文处理器，但在每个控制器方法前执行。
  • 订单和订单项是一个聚合：cascade = ALL，在一个事务里保存。
  • 异步任务：事件 → AFTER_COMMIT → RabbitTemplate → @RabbitListener。
  • 表格编辑 = 绑定 List，复选框靠隐藏的 _ 字段表示“未勾选”。
