Spring Boot 版 · 第 10 章 · 项目三：在线商店

扩展商店

这一章给商店加两个常见功能：优惠券（输入代码打折，并把折扣带到 Stripe 支付页）和“买了这个的人也买了”推荐。 优惠券涉及会话、金额计算和外键的 SET NULL；推荐引擎用 Redis 有序集合统计商品共同购买的次数。 顺带还要解决一个测试基础设施的问题：为什么多个测试类会把机器拖垮。

本章目标

  • 建模优惠券，按“代码 + 有效期 + 启用”查询有效券
  • 把优惠券 id 存进会话，计算折扣时统一处理金额的精度和舍入
  • 订单记录优惠券和折扣百分比，理解 ON DELETE SET NULL 和“冗余保存”
  • 在 Stripe 上即时创建优惠券并附加到 Checkout Session
  • 用 Redis 有序集合（ZINCRBY、ZUNIONSTORE）实现推荐引擎
  • 在支付成功事件的 AFTER_COMMIT 阶段写 Redis
  • 让所有集成测试共享同一个 Spring 上下文和同一组容器

对应的 Django 讲解见 Django 版第 10 章；本章代码在 springboot/Chapter10/。

ⓘ 校验器 vs 数据库约束

Django 的 MinValueValidator/MaxValueValidator 只在表单（ModelForm、admin）校验时生效，直接 Coupon.objects.create(discount=150) 不会报错。Spring 版除了表单上的 @Min/@Max，还在迁移里加了 CHECK 约束，由数据库兜底。Django 也可以用 Meta.constraints = [CheckConstraint(...)] 做到。

折扣与金额

优惠券 id 存在会话里（第 8 章的 Cart 多了一个 couponId 字段）。购物车的金额计算集中在 CartService：

Django · cart/cart.py
@property
def coupon(self):
    if self.coupon_id:
        try:
            return Coupon.objects.get(id=self.coupon_id)
        except Coupon.DoesNotExist:
            pass
    return None

def get_discount(self):
    if self.coupon:
        return (self.coupon.discount / Decimal(100)) \
               * self.get_total_price()
    return Decimal(0)

def get_total_price_after_discount(self):
    return self.get_total_price() - self.get_discount()
Spring · cart/CartService.java
public record Totals(BigDecimal subtotal, Coupon coupon,
                     BigDecimal discount) {
    public BigDecimal total() {
        return subtotal.subtract(discount);
    }
}

public Totals totals() {
    BigDecimal subtotal = cart.totalPrice();
    Coupon coupon = coupon();
    BigDecimal discount = coupon == null ? BigDecimal.ZERO
            : Money.percentOf(subtotal, coupon.getDiscount());
    return new Totals(subtotal, coupon, discount);
}

// common/Money.java
public static BigDecimal percentOf(BigDecimal amount, int percent) {
    return amount.multiply(BigDecimal.valueOf(percent))
            .divide(BigDecimal.valueOf(100), 2, RoundingMode.HALF_UP);
}
⚠ 舍入要在计算时做，而不是显示时

书中 get_discount() 返回的是任意精度的 Decimal（比如 13.550000），模板里用 floatformat:2 显示时才四舍五入。 这样页面上显示的“小计 − 折扣”可能和“总计”差一分钱。Spring 版在计算时就统一保留两位小数、四舍五入，显示和存储的数字完全一致。 BigDecimal.divide 不指定精度时，遇到除不尽的数还会直接抛异常 —— 这反而是好事，逼你想清楚舍入规则。

/** ForeignKey(Coupon, null=True, on_delete=SET_NULL)：优惠券被删了，订单还在 */

@Column(nullable = false)

public void applyCoupon(Coupon coupon) {
    this.coupon = coupon;
    this.discount = coupon == null ? 0 : coupon.getDiscount();
}

ALTER TABLE orders_order ADD COLUMN coupon_id BIGINT REFERENCES coupons_coupon (id) ON DELETE SET NULL;
ALTER TABLE orders_order ADD COLUMN discount INTEGER NOT NULL DEFAULT 0 CHECK (discount BETWEEN 0 AND 100);

Django 的 on_delete=SET_NULL 是在 ORM 层模拟的（删除优惠券前先 UPDATE 订单）；Spring 版直接写成数据库的外键动作。 discount 冗余保存和订单项保存下单时的价格是一个道理：订单是“历史记录”，不应该随着别的数据变化。

显示折扣：一个可复用的模板片段

购物车、支付页、PDF、后台订单详情都要显示“小计 / 优惠券 / 折扣”三行。Django 版把同样的 HTML 复制了四遍；Spring 版写成一个带参数的片段：

<th:block th:fragment="discountRows(subtotal, coupon, percent, discount, span)">
  <tr class="subtotal" th:if="${coupon != null}">
    <td>Subtotal</td><td th:colspan="${span}"></td>
    <td class="num" th:text="${'$' + subtotal}">$0</td>
  </tr>
  <tr th:if="${coupon != null}">
    <td th:text="|&quot;${coupon.code}&quot; coupon (${percent}% off)|"></td>
    <td th:colspan="${span}"></td>
    <td class="num neg" th:text="${'- $' + discount}">- $0</td>
  </tr>
</th:block>

<!-- 购物车里（表格有 6 列，中间空 4 列） -->
<th:block th:replace="~{fragments/money :: discountRows(${totals.subtotal}, ${totals.coupon},
          ${totals.coupon?.discount}, ${totals.discount}, 4)}"></th:block>

${totals.coupon?.discount} 里的 ?. 是 SpEL 的安全导航：coupon 为 null 时整个表达式为 null，而不是抛异常。

推荐引擎：Redis 有序集合

思路：每卖出一笔订单，就把订单里的商品两两“配对”，给每个商品记一个有序集合：product:{id}:purchased_with，成员是一起买过的商品 id，分数是一起买的次数。

public void productsBought(Collection<Long> productIds) {
    for (Long productId : productIds) {
        for (Long withId : productIds) {
            if (!productId.equals(withId)) {
                redis.opsForZSet().incrementScore(key(productId), withId.toString(), 1);   // ZINCRBY
            }
        }
    }
}

⚠ 书中临时键名的问题

书中用 ''.join([str(id) for id in product_ids]) 拼临时键名：[1, 23] 和 [12, 3] 都会得到 tmp_123， 两个用户同时查看这样的购物车，就会读到对方的合并结果（甚至被对方删掉）。Spring 版用 UUID 生成唯一的临时键。更进一步，可以用 Lua 脚本或事务（MULTI/EXEC）把这几步合成一个原子操作。

什么时候记录“一起购买”

书中在 Webhook 视图里、标记已付款之后直接调用 r.products_bought(products)。Spring 版把它放在支付成功事件的监听器里，而且等事务提交后再执行：

@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
@Transactional(propagation = Propagation.REQUIRES_NEW, readOnly = true)
public void onPaymentCompleted(PaymentCompletedEvent event) {
    orders.findWithItemsById(event.orderId()).ifPresent(order ->
            recommender.productsBought(order.getItems().stream()
                    .map(item -> item.getProduct().getId()).distinct().toList()));
}
  • 为什么 AFTER_COMMIT：Redis 不参与数据库事务。如果支付状态的事务回滚了，Redis 里的计数却已经加上，就会“凭空”多出购买记录。
  • 为什么 REQUIRES_NEW：AFTER_COMMIT 阶段原来的事务已经结束，这里要查订单项，得开一个新的（只读）事务。
  • 同一个 PaymentCompletedEvent 现在有两个监听者：发发票任务（第 9 章）和记推荐数据（本章）。发布事件的 PaymentService 一行都不用改 —— 这就是事件解耦的好处。

测试基础设施：共享上下文

本章第一次运行测试时，有一个测试类等了将近 15 分钟，最后 RabbitMQ 容器启动超时。原因是：各测试类的 @MockitoBean 组合不同 （有的 mock 了邮件，有的还 mock 了 Stripe 网关），Spring 就为每种组合创建一个新的应用上下文，每个上下文又启动一套 RabbitMQ + Redis 容器。 几套容器同时运行，把机器拖垮了。 

/**
 * Spring 会缓存测试用的应用上下文，但前提是“配置完全一样”——包括 @MockitoBean 替换了哪些 Bean。
 * 把会用到的 mock 统一放在基类里，所有测试类共享同一个上下文。
 */
@SpringBootTest
@AutoConfigureMockMvc
@ActiveProfiles("test")
@Import(TestcontainersConfiguration.class)
public abstract class IntegrationTest {

    @MockitoBean
    protected JavaMailSender mailSender;

    @MockitoBean
    protected StripeGateway gateway;
}

// TestcontainersConfiguration：容器放在静态字段里，即使有多个上下文也只启动一次
static final RabbitMQContainer RABBIT = new RabbitMQContainer("rabbitmq:3.13-management");
static final GenericContainer<?> REDIS = new GenericContainer<>("redis:7.2").withExposedPorts(6379);

改完之后，20 个测试共用一个上下文，整套测试从十几分钟（最后超时失败）降到一两分钟。这个结构也同步回了第 8、9 章。Django 的测试运行器只有一个进程级的设置，天然不会有这个问题；Spring 的上下文缓存是提速利器，但要有意识地“喂”它相同的配置。

ⓘ 共享的 Redis 不会回滚

测试事务只回滚数据库。推荐测试和发票测试都会写 Redis，所以相关测试在开始前执行 FLUSHDB，否则上一个测试留下的购买记录会让断言失败 —— 这也是本章实际踩到的坑。

本章共 20 个测试：优惠券（大小写不敏感、过期和停用、订单保存折扣、后台校验）、推荐引擎（单个与多个商品、临时键已删除、顺序）、支付成功后写入推荐数据，以及前两章的全部测试。

差异点评

🔍 第 10 章 Spring 版点评 springboot/Chapter10

做得好 金额在计算时统一舍入

页面、Stripe、PDF 看到的是同一个两位小数，不会差一分钱。

做得好 临时键唯一、Redis 写入时机正确

修正了书中临时键名冲突的问题；推荐数据在支付状态提交后才写入。

注意 优惠券没有使用次数限制

和书中一样，一张券在有效期内可以无限次使用。实际业务通常要“每人一次”或“总量有限”，那就需要记录使用情况，并在下单时加锁或用条件更新防止超发（见 专题 4 的并发一节）。

注意 下单时没有重新校验优惠券

会话里的券在“应用”时有效，下单时可能已经过期或被停用。OrderService.create() 应该再调用一次 findValid。书中也有同样的问题。

补充知识 推荐数据可以离线重建

Redis 里的推荐数据完全可以从订单表重新计算出来。书中提供了 clear_purchases()；可以再写一个“命令”遍历所有已付款订单重建推荐（第 17 章讲命令行任务）。

小结

  • 优惠券：JPQL 查询有效券，id 存会话；表单用 record。
  • 金额计算用 BigDecimal + 明确的舍入规则；订单冗余保存折扣百分比，外键 SET NULL。
  • 重复的 HTML 抽成带参数的 Thymeleaf 片段；?. 安全导航。
  • 推荐引擎：incrementScore、unionAndStore、reverseRange；临时键要唯一。
  • 同一事件可以有多个监听者；写 Redis 放在 AFTER_COMMIT。
  • 集成测试共享一个基类和一组静态容器，充分利用上下文缓存。
