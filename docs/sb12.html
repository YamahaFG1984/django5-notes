Spring Boot 版 · 第 12 章 · 项目四：在线学习平台

构建在线学习平台

最后一个项目 Educa 是一个在线学习平台：讲师创建课程，课程分成模块，模块里放各种类型的内容（文字、图片、视频、文件）。 这一章只搭数据模型，但它集中了 ORM 里最有意思的几个话题：初始数据（fixtures）、模型继承、 指向“任意一种模型”的外键，以及自定义字段。Django 用 GenericForeignKey 和自定义 OrderField 解决； JPA 的答案是继承映射和实体监听器 —— 思路不同，但结果更“关系型”。

本章目标

  • 建立 Subject → Course → Module → Content 的模型，理解 @OrderBy 与 Meta.ordering 的区别
  • 写一个 --loaddata 命令读取 Django 格式的 fixture，并处理“显式主键后序列不前进”的问题
  • 对比 Django 的三种模型继承与 JPA 的三种继承策略，用 JOINED 继承代替 GenericForeignKey
  • 用自定义注解 + JPA 实体监听器实现 OrderField，并让监听器成为 Spring Bean
  • 用户组与权限代码：为下一章的权限控制做准备

对应的 Django 讲解见 Django 版第 12 章；本章代码在 springboot/Chapter12/。

全景：数据模型

项目与账户

Educa 和前几章一样用 H2 文件库（原书这几章用 SQLite，第 17 章两边都换成 PostgreSQL），Flyway 手写迁移， ddl-auto=validate 让 Hibernate 在启动时检查实体和表结构是否一致。本章新出现的是用户组与权限： Django 为每个模型自动生成 add_/change_/delete_/view_ 四个权限，组把权限打包，再把用户加进组。

Django · contrib.auth（自动生成）
# 迁移时自动为 Course 创建四个权限：
#   courses.add_course / change_course /
#   delete_course / view_course
user.has_perm('courses.add_course')
# 超级用户永远返回 True
Spring · 权限代码作为 authority
// CurrentUser.from(user)：权限来自用户所在的组
Set<String> names = new LinkedHashSet<>();
names.add("ROLE_USER");
if (user.isSuperuser()) {
    names.add("ROLE_ADMIN");
    names.addAll(Permissions.ALL);   // ≈ 超级用户拥有全部权限
}
user.getGroups().forEach(g -> names.addAll(g.getPermissions()));
  • Spring Security 只有一个概念：GrantedAuthority（一个字符串）。“角色”只是带 ROLE_ 前缀的 authority；权限代码 courses.add_course 直接作为 authority 放进去，下一章用 hasAuthority('courses.add_course') 检查。
  • 表结构简化为 auth_group、auth_group_permissions(group_id, codename)、auth_user_groups，组的权限用 @ElementCollection Set<String> 映射。Django 还有一张 auth_permission 表和 content_type 关联，这里用不上。
  • 登录时用 @EntityGraph(attributePaths = {"groups", "groups.permissions"}) 一次查出用户、组和权限。

课程、模块与排序

Django · models.py
class Course(models.Model):
    owner = models.ForeignKey(User,
        related_name='courses_created', on_delete=models.CASCADE)
    subject = models.ForeignKey(Subject,
        related_name='courses', on_delete=models.CASCADE)
    title = models.CharField(max_length=200)
    slug = models.SlugField(max_length=200, unique=True)
    overview = models.TextField()
    created = models.DateTimeField(auto_now_add=True)

    class Meta:
        ordering = ['-created']

class Module(models.Model):
    course = models.ForeignKey(Course,
        related_name='modules', on_delete=models.CASCADE)
    ...
    order = OrderField(blank=True, for_fields=['course'])

    class Meta:
        ordering = ['order']
Spring · Course.java / Module.java
@Entity @Table(name = "courses_course")
public class Course {
    @ManyToOne(fetch = LAZY, optional = false)
    @JoinColumn(name = "owner_id")
    private User owner;
    ...
    /** related_name='modules'；Module 的 ordering = ['order'] */
    @OneToMany(mappedBy = "course", cascade = ALL, orphanRemoval = true)
    @OrderBy("order")
    private List<Module> modules = new ArrayList<>();
}

@Entity @Table(name = "courses_module")
@EntityListeners(OrderFieldListener.class)
public class Module {
    @OrderField(scope = "course")
    @Column(name = "\"order\"", nullable = false)
    private Integer order;
}
  • 默认排序：Django 的 Meta.ordering 作用于该模型的所有查询。JPA 没有全局默认排序：@OrderBy 只作用于集合属性（course.getModules()），仓库查询要在方法名里写 OrderByOrderAsc 或在 JPQL 里写 order by。好处是排序总是显式可见的。
  • 反向关系：related_name='modules' 在 JPA 里是 mappedBy 的一对多集合，需要时才声明。courses_created 这类用得少的反向关系就不声明，用仓库方法 findByOwnerId 查询即可。
  • 关键字列名：order 是 SQL 保留字。Django 自动给列名加引号；JPA 要自己写 @Column(name = "\"order\"")，迁移脚本里同样要写 "order"。
  • 级联删除：on_delete=CASCADE 在 Django 里由 ORM 模拟；这里在迁移脚本的外键上写 ON DELETE CASCADE，由数据库保证；实体上的 cascade = ALL, orphanRemoval = true 让通过 JPA 删除课程时也把模块一起删掉。

初始数据：fixtures 与 loaddata

书中先在 Admin 里录入几个学科，用 dumpdata 导出成 courses/fixtures/subjects.json，新环境里 loaddata subjects 一键导入。 Spring 没有 fixture 机制。常见做法有两种：写成 Flyway 的数据迁移（INSERT 语句），或者写一个导入命令。 学科属于“示例数据”而不是“表结构的一部分”，所以这里选后者 —— 并且直接读取 Django 导出的同一个 JSON 文件。

Django · 命令行
python manage.py dumpdata courses --indent=2 \
    --output=courses/fixtures/subjects.json
python manage.py loaddata subjects.json
# Installed 4 object(s) from 1 fixture(s)
Spring · 同一个 JSON，自己写的命令
# fixtures/subjects.json 放在 src/main/resources 下
java -jar target/educa-1.0.0.jar --loaddata=subjects
# Installed 4 object(s) from 1 fixture(s)

/** 整个文件在一个事务里导入：要么全部成功，要么什么都不改（loaddata 也是这样） */
public int load(String name) {
    List<FixtureObject> objects = List.of(objectMapper.readValue(in, FixtureObject[].class));
    return transactions.execute(status -> {
        for (FixtureObject object : objects) {
            subjects.upsert(object.pk(), object.fields().title(), object.fields().slug());
        }
        resetIdentity("courses_subject");
        return objects.size();
    });
}

// SubjectRepository：按主键“有则更新、无则插入”（loaddata 的语义），SQL 标准的 MERGE
@Modifying(clearAutomatically = true)
@NativeQuery("""
        MERGE INTO courses_subject t
        USING (VALUES (CAST(:id AS BIGINT), CAST(:title AS VARCHAR(200)), CAST(:slug AS VARCHAR(200)))) AS v(id, title, slug)
        ON t.id = v.id
        WHEN MATCHED THEN UPDATE SET title = v.title, slug = v.slug
        WHEN NOT MATCHED THEN INSERT (id, title, slug) VALUES (v.id, v.title, v.slug)
        """)
void upsert(@Param("id") Long id, @Param("title") String title, @Param("slug") String slug);
⚠ 显式插入主键之后，要把序列往前推

fixture 里带着主键（"pk": 1）。用显式主键插入后，数据库的自增序列并不会跟着前进 —— 下一次普通插入拿到的新主键还是 1，立刻主键冲突。Django 的 loaddata 会在最后自动执行 sqlsequencereset， 我们只能自己做，而且 H2 和 PostgreSQL 的语法不同：H2 用 ALTER TABLE … ALTER COLUMN id RESTART WITH n， PostgreSQL 用 setval(pg_get_serial_sequence(...), max)。这正是 ORM 平时替我们屏蔽掉的差异；第 17 章会在真正的 PostgreSQL 上测试这段代码。

命令的写法和第 1 章的 --createsuperuser 一样：一个 ApplicationRunner，只在命令行带了 --loaddata 时执行，执行完主动退出。 因为是 Web 应用，Tomcat 已经启动了，所以要调用 SpringApplication.exit() 关掉容器，否则进程不会结束。

多态内容：GenericForeignKey 与 JPA 继承

模块里的“内容”可以是文字、视频、图片或文件，它们有公共字段（owner、title、created、updated），也有各自的字段。 问题是：Content 怎么指向“四种模型中的任意一种”？

Django 的模型继承JPA 的对应做法表结构
抽象基类 abstract = True（书中 ItemBase 用的）@MappedSuperclass没有公共表，每个子类一张完整的表
多表继承（父类是普通模型）@Inheritance(strategy = JOINED)（本项目用的）公共字段一张表，子类各一张表，主键相同
代理模型 proxy = True没有直接对应（可以用同一张表的不同实体类或普通 Java 子类）共用父类的表
—@Inheritance(strategy = SINGLE_TABLE)所有子类挤进一张表，用类型列区分，子类字段必须可空

书中选了抽象基类，于是四种条目是四张毫无关系的表，Content 只能用 GenericForeignKey： 存一个 content_type（哪张表）加一个 object_id（哪一行）。它很灵活，但数据库层面没有外键约束， 也不能 join 查询。JPA 的 JOINED 继承给了四个子类一张公共父表 courses_item，Content.item_id 就可以是真正的外键：

Django · 抽象基类 + 泛型外键
class ItemBase(models.Model):
    owner = models.ForeignKey(User,
        related_name='%(class)s_related', ...)
    title = models.CharField(max_length=250)
    created = models.DateTimeField(auto_now_add=True)
    updated = models.DateTimeField(auto_now=True)
    class Meta:
        abstract = True

class Text(ItemBase):
    content = models.TextField()

class Content(models.Model):
    module = models.ForeignKey(Module, ...)
    content_type = models.ForeignKey(ContentType,
        limit_choices_to={'model__in': (
            'text', 'video', 'image', 'file')}, ...)
    object_id = models.PositiveIntegerField()
    item = GenericForeignKey('content_type', 'object_id')
    order = OrderField(blank=True, for_fields=['module'])
Spring · JOINED 继承 + 普通外键
@Entity @Table(name = "courses_item")
@Inheritance(strategy = InheritanceType.JOINED)
@DiscriminatorColumn(name = "item_type", length = 20)
public abstract class Item {
    @ManyToOne(fetch = LAZY, optional = false)
    private User owner;
    private String title;
    @CreationTimestamp private OffsetDateTime created;
    @UpdateTimestamp   private OffsetDateTime updated;

    /** ≈ item._meta.model_name */
    public abstract String getModelName();
}

@Entity @Table(name = "courses_text")
@DiscriminatorValue("text")
@PrimaryKeyJoinColumn(name = "item_id")
public class TextItem extends Item {
    private String content;
}

@Entity @Table(name = "courses_content")
public class Content {
    @ManyToOne(fetch = LAZY, optional = false)
    private Module module;
    @OneToOne(fetch = LAZY, optional = false,
              cascade = ALL, orphanRemoval = true)
    @JoinColumn(name = "item_id", unique = true)
    private Item item;   // 真正的外键
}
  • 查询：加载 Content 时 Hibernate 用 left join 把父表和所有子表连起来，按鉴别列 item_type 实例化 TextItem、VideoItem…… 模板里调用 item.getModelName() 即可，不需要书中自定义的 model_name 过滤器。
  • 多态查询：select i from Item i where i.owner = :owner 一次查出某个讲师的所有条目，不管什么类型 —— 泛型外键做不到这一点。
  • 删除：cascade = ALL, orphanRemoval = true 让删除 Content 时自动删除它的条目；书中要先 content.item.delete() 再 content.delete()（第 13 章的 ContentDeleteView）。
  • 代价：每加一种内容类型，要新建一张子表并修改迁移；JOINED 查询要多 join 几张表。对这个项目的规模来说完全不是问题。
⚠ 懒加载的父类引用是“代理”

Content.item 是 LAZY 的。如果没有用 @EntityGraph 或 join fetch 把它一起查出来， content.getItem() 返回的是 Hibernate 生成的 Item 代理子类，不是 TextItem， instanceof TextItem 和 switch 模式匹配都会失败。需要按具体类型处理时，先 Hibernate.unproxy(item)。 第 14、15 章都会遇到这个问题。

自定义排序字段：注解 + 实体监听器

书中写了一个 OrderField：保存新对象时，如果没指定顺序，就取“同一门课程（或同一个模块）里最大的序号 + 1”。 Django 的做法是继承 PositiveIntegerField 并重写 pre_save()。 JPA 没有“自定义字段类型带保存逻辑”这种东西，对应的机制是实体生命周期回调：@PrePersist、@PreUpdate…… 再配一个注解标出“哪个字段、按什么范围编号”：

Django · fields.py
class OrderField(models.PositiveIntegerField):
    def __init__(self, for_fields=None, *args, **kwargs):
        self.for_fields = for_fields
        super().__init__(*args, **kwargs)

    def pre_save(self, model_instance, add):
        if getattr(model_instance, self.attname) is None:
            try:
                qs = self.model.objects.all()
                if self.for_fields:
                    query = {field: getattr(model_instance, field)
                             for field in self.for_fields}
                    qs = qs.filter(**query)
                last_item = qs.latest(self.attname)
                value = getattr(last_item, self.attname) + 1
            except ObjectDoesNotExist:
                value = 0
            setattr(model_instance, self.attname, value)
            return value
        return super().pre_save(model_instance, add)
Spring · OrderField + OrderFieldListener
@Target(FIELD) @Retention(RUNTIME)
public @interface OrderField {
    String scope();   // ≈ for_fields
}

@Component
public class OrderFieldListener {
    private final ObjectProvider<EntityManagerFactory> emf;

    @PrePersist
    public void assignOrder(Object entity) {
        ReflectionUtils.doWithFields(entity.getClass(), field -> {
            ... // 已有值就跳过
            EntityManager em = EntityManagerFactoryUtils
                    .getTransactionalEntityManager(emf.getObject());
            Integer max = em.createQuery(
                    "select max(e.%s) from %s e where e.%s = :scope"
                        .formatted(...), Integer.class)
                .setParameter("scope", scope)
                .setFlushMode(FlushModeType.COMMIT)
                .getSingleResult();
            field.set(entity, max == null ? 0 : max + 1);
        }, f -> f.isAnnotationPresent(OrderField.class));
    }
}

要让它工作，有三个细节，每一个都是真实踩过的坑：

  1. 监听器默认不是 Spring Bean。JPA 规范规定监听器由持久化提供者（Hibernate）用无参构造器创建，里面 @Autowired 的字段全是 null。 要让 Hibernate 从 Spring 容器里取监听器，得告诉它用 SpringBeanContainer： 
    @Bean
HibernatePropertiesCustomizer springBeanContainer(ConfigurableListableBeanFactory beanFactory) {
    return props -> props.put(AvailableSettings.BEAN_CONTAINER, new SpringBeanContainer(beanFactory));
}
  2. 不能直接注入 EntityManager。监听器是在构建 EntityManagerFactory 的过程中创建的，这时工厂本身还不存在 —— 构造器注入会形成循环依赖。 解决办法是注入 ObjectProvider<EntityManagerFactory>，用到时再取，并通过 EntityManagerFactoryUtils 拿到当前事务绑定的 EntityManager。
  3. 查询时不能触发自动 flush。@PrePersist 发生在 persist 的过程中，这时再执行查询，Hibernate 默认会先 flush 持久化上下文 —— 正在保存的这个对象还没准备好，可能导致异常或重复插入。setFlushMode(FlushModeType.COMMIT) 让这次查询跳过自动 flush。

这样一来，Module 和 Content 上各加一个 @OrderField(scope = "course") / @OrderField(scope = "module") 和 @EntityListeners(OrderFieldListener.class) 就有了和书中一样的行为。

登录与登出

书中直接使用 django.contrib.auth 的 LoginView 和 LogoutView。Spring 这边在 SecurityConfig 里配置表单登录， 两个只渲染模板的页面用 ViewControllerRegistry 注册（≈ 只有 template_name 的 TemplateView）： 

http.formLogin(form -> form.loginPage("/accounts/login/").defaultSuccessUrl("/").permitAll())
    .logout(logout -> logout.logoutUrl("/accounts/logout/").logoutSuccessUrl("/accounts/logged-out/"));

registry.addViewController("/accounts/login/").setViewName("registration/login");
registry.addViewController("/accounts/logged-out/").setViewName("registration/logged_out");

登出必须用 POST（Django 5 起 LogoutView 也不再接受 GET），所以 base.html 里的 “Sign out” 是一个带 CSRF 令牌的小表单。 书中这一章还用 Django Admin 录入课程和模块（ModuleInline）；Spring 版没有 Admin，下一章直接做讲师自己的课程管理界面。

差异点评

🔍 第 12 章 Spring 版点评 springboot/Chapter12

做得好 用真正的外键代替泛型外键

数据库能保证 Content 指向的条目一定存在；可以 join、可以多态查询；删除时由级联处理，不会留下孤儿行。

做得好 fixture 格式保持兼容

直接读取 Django 的 subjects.json，导入在一个事务里完成，可以重复执行，并处理了序列重置。

注意 “最大值 + 1”有并发问题（书中也一样）

两个请求同时给同一门课添加模块，可能读到同一个最大值，得到两个相同的序号。数据库里没有 unique(course_id, "order") 约束，所以不会报错，只是顺序不确定。要彻底避免，可以在添加时锁住课程行（@Lock(PESSIMISTIC_WRITE)），或者接受这种情况 —— 下一章的拖拽排序会把序号重新写一遍。

注意 没有 Admin

Django Admin 让你零代码录入课程、模块（内联编辑）；Spring 版这一章只能通过测试或命令行造数据，下一章的讲师后台才补上界面。

补充知识 什么时候仍然需要“泛型外键”

如果被引用的类型事先不知道、或者来自不同的模块（比如“评论可以挂在任何东西上”），继承就不合适了。JPA 里可以用 Hibernate 的 @Any 映射，或者像第 7 章的活动流那样手工存 target_type + target_id，自己负责加载。

小结

  • 权限代码直接作为 GrantedAuthority，来自用户所在的组；超级用户拥有全部权限。
  • JPA 没有全局默认排序：集合用 @OrderBy，查询自己写排序。
  • fixture 用自定义 --loaddata 命令导入：MERGE 按主键 upsert，最后重置自增序列。
  • @Inheritance(JOINED) 给多种内容类型一张公共父表，Content 用真正的外键指向它；懒加载的引用是代理，按类型处理前要 unproxy。
  • 自定义保存逻辑用实体监听器；监听器要成为 Spring Bean 需要 SpringBeanContainer，依赖 EntityManagerFactory 时用 ObjectProvider 延迟获取。
