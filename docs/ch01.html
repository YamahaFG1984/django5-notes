创建博客应用

这一章从零搭起一个能跑的博客：装好 Python 和 Django，建项目、建应用， 设计数据模型并同步到数据库，配一个管理后台，再用视图、URL 和模板把文章展示出来。 学完你会对 Django 处理一个请求的完整路线有一张清晰的“地图”。

  • 写出 Post 模型：字段、默认排序、索引、枚举选项、外键

  • 用 ModelAdmin 定制管理后台

Django 是怎么工作的

Django 是一个“电池全包”的 Python Web 框架：数据库访问、表单、用户认证、管理后台、缓存、国际化…… 这些网站常见需求它都内置了。它的组件是松耦合的 —— 数据库层不知道数据会怎么显示， 模板系统也不关心请求从哪来 —— 所以每一块都能单独理解、单独替换。

Django 采用 MTV（Model-Template-View）模式。如果你听说过 MVC，可以这样对照：

MTV 中的角色负责什么对应 MVC 里的在哪个文件
Model 模型定义数据结构，负责和数据库打交道Modelmodels.py
Template 模板展示层：决定数据长什么样（HTML）Viewtemplates/*.html
View 视图业务逻辑：取数据、交给模板、返回响应Controller（的一部分）views.py
框架本身按 URL 配置把请求派发给正确的视图Controllerurls.py
  1. 浏览器按 URL 请求页面，Web 服务器把 HTTP 请求交给 Django。
  2. Django 按顺序比对 URL 模式，停在第一个匹配的，调用对应的视图。
  3. 视图通过模型查询数据库（ORM 会把 Python 调用翻译成 SQL）。
  4. 视图把数据交给模板，渲染出 HTML。
  5. 视图返回一个 HttpResponse，浏览器显示页面。
ⓘ 图里省略了中间件

真实的请求在到达视图之前、响应在离开视图之后，还会穿过一层层中间件（middleware）， 比如会话、CSRF 校验、用户认证。本章末尾的请求/响应图会把它画出来，第 17 章会教你自己写一个。

项目与应用

这是 Django 最先要搞清的两个词：

  • 项目（project）：一个网站的整体配置 —— 数据库连哪、启用了哪些应用、根 URL 是什么。
  • 应用（app）：一块独立的功能，包含自己的模型、视图、模板和 URL。比如博客、论坛、购物车。一个应用可以被多个项目复用。
django-admin startproject mysite   # 创建项目（别用 django、test 这类会和内置模块重名的名字）
cd mysite
python manage.py migrate           # 为内置应用（auth、admin、sessions…）建表
python manage.py runserver         # 启动开发服务器 → http://127.0.0.1:8000/
python manage.py startapp blog     # 创建 blog 应用

mysite/                 ← 外层：只是个容器，名字随便改
├── manage.py           ← 命令行工具，几乎不用改
├── mysite/             ← 项目的 Python 包
│   ├── __init__.py
│   ├── settings.py     ← 所有配置
│   ├── urls.py         ← 根 URL 配置

│   └── wsgi.py         ← 同步服务器入口（第 17 章用）

⚠ runserver 只能用来开发

开发服务器会自动重载代码，但它没做过安全和性能加固。生产环境要用 Gunicorn / uWSGI（WSGI） 或 Daphne / Uvicorn（ASGI），第 17 章会讲。另外新增文件时自动重载有时察觉不到，需要手动重启。

设计数据模型

模型就是一个继承 django.db.models.Model 的 Python 类。 一个模型对应数据库里一张表，类里的每个字段属性对应表里的一列。 我们一步步把博客文章模型 Post 搭起来。

第一步：最基本的字段

from django.db import models


class Post(models.Model):
    title = models.CharField(max_length=250)   # → VARCHAR(250)
    slug = models.SlugField(max_length=250)    # → VARCHAR(250)，默认带索引
    body = models.TextField()                  # → TEXT

    def __str__(self):
        return self.title                      # 在 Admin、shell 里显示的名字

slug 是一个只含字母、数字、下划线、连字符的短标签，用来做好看的 URL。 比如标题 “Django Reinhardt: A legend of Jazz” 的 slug 可以是 django-reinhardt-legend-jazz。 你没有定义主键时，Django 会自动加一个自增的 id（类型由 DEFAULT_AUTO_FIELD 决定，默认 64 位的 BigAutoField）。

第二步：时间、排序与索引

from django.utils import timezone


class Post(models.Model):
    # ...
    publish = models.DateTimeField(default=timezone.now)  # 发布时间，默认“现在”
    created = models.DateTimeField(auto_now_add=True)     # 创建时自动填，之后不变
    updated = models.DateTimeField(auto_now=True)         # 每次 save() 都自动更新

    class Meta:
        ordering = ['-publish']                  # 默认按发布时间倒序
        indexes = [
            models.Index(fields=['-publish']),   # 为排序字段建降序索引
        ]
★ default=timezone.now 不要写成 timezone.now()

传的是函数本身，Django 每次创建对象时调用它；加了括号就变成“模块加载那一刻的时间”，所有文章都会是同一个时间。 Django 5 还可以写 db_default=Now()，让数据库用 NOW() 生成默认值。

第三步：状态字段 —— 用枚举类定义选项

class Post(models.Model):
    class Status(models.TextChoices):
        DRAFT = 'DF', 'Draft'            # 存进数据库的值, 给人看的标签
        PUBLISHED = 'PB', 'Published'

    # ...
    status = models.CharField(
        max_length=2,
        choices=Status,                  # Django 5 起可以直接传枚举类
        default=Status.DRAFT,
    )

>>> Post.Status.choices     # [('DF', 'Draft'), ('PB', 'Published')]
>>> Post.Status.labels      # ['Draft', 'Published']
>>> Post.Status.values      # ['DF', 'PB']
>>> Post.Status.names       # ['DRAFT', 'PUBLISHED']
>>> Post.Status.PUBLISHED   # 在代码任何地方都用它，而不是写死 'PB'

第四步：作者 —— 多对一关系

from django.conf import settings


class Post(models.Model):
    # ...
    author = models.ForeignKey(
        settings.AUTH_USER_MODEL,        # 指向“当前项目的用户模型”，而不是写死 User
        on_delete=models.CASCADE,        # 用户被删，他的文章一起删
        related_name='blog_posts',       # 反向访问名：user.blog_posts.all()
    )
ⓘ on_delete 的常见取值

CASCADE 级联删除；PROTECT 有关联时禁止删除；SET_NULL 置空（字段要 null=True）； SET_DEFAULT 设为默认值；RESTRICT 类似 PROTECT 但允许被级联删除。 文章跟着作者一起删未必合理 —— 真实项目里经常用 PROTECT 或软删除，见本章末的点评。

完整的 Post 模型

最后加上自定义管理器和 get_absolute_url()（后者第 2 章详细讲），就是仓库里 Chapter01/mysite/blog/models.py 的样子：

from django.conf import settings
from django.db import models
from django.urls import reverse
from django.utils import timezone


class PublishedManager(models.Manager):
    def get_queryset(self):
        return super().get_queryset().filter(status=Post.Status.PUBLISHED)


class Post(models.Model):
    class Status(models.TextChoices):
        DRAFT = 'DF', 'Draft'
        PUBLISHED = 'PB', 'Published'

    title = models.CharField(max_length=250)
    slug = models.SlugField(max_length=250)
    author = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.CASCADE,
        related_name='blog_posts',
    )
    body = models.TextField()
    publish = models.DateTimeField(default=timezone.now)
    created = models.DateTimeField(auto_now_add=True)
    updated = models.DateTimeField(auto_now=True)
    status = models.CharField(max_length=2, choices=Status, default=Status.DRAFT)

    objects = models.Manager()        # 默认管理器
    published = PublishedManager()    # 自定义管理器

    class Meta:
        ordering = ['-publish']
        indexes = [models.Index(fields=['-publish'])]

    def __str__(self):
        return self.title

    def get_absolute_url(self):
        return reverse('blog:post_detail', args=[self.id])

迁移：把模型同步到数据库

你改了 models.py，数据库并不会自动跟着变。Django 的迁移系统记录模型的每一次变化， 生成可以提交到 Git 的迁移文件，再把这些变化应用到数据库。 

python manage.py makemigrations blog     # 生成 blog/migrations/0001_initial.py
python manage.py sqlmigrate blog 0001    # 看看它会执行什么 SQL
python manage.py migrate                 # 真正应用到数据库

BEGIN;
-- Create model Post
CREATE TABLE "blog_post" (
  "id" integer NOT NULL PRIMARY KEY AUTOINCREMENT,
  "title" varchar(250) NOT NULL,
  "slug" varchar(250) NOT NULL,
  "body" text NOT NULL,
  "publish" datetime NOT NULL,
  "created" datetime NOT NULL,
  "updated" datetime NOT NULL,
  "status" varchar(10) NOT NULL,
  "author_id" integer NOT NULL REFERENCES "auth_user" ("id") DEFERRABLE INITIALLY DEFERRED);
CREATE INDEX "blog_post_publish_bb7600_idx" ON "blog_post" ("publish" DESC);
CREATE INDEX "blog_post_slug_b95473f2" ON "blog_post" ("slug");
CREATE INDEX "blog_post_author_id_dd7a8485" ON "blog_post" ("author_id");
COMMIT;

注意这里自动建了三个索引：我们在 Meta.indexes 里声明的 publish 降序索引，以及 SlugField 和 ForeignKey 默认附带的索引。

⚠ 迁移文件是代码，要提交、要审查

团队开发时，每个人都用同一套迁移文件重建数据库。不要把 migrations/ 加进 .gitignore， 也不要随手删掉已经被别人应用过的迁移。

管理后台

Django 最出名的“杀手锏”之一：读取模型的元数据，自动生成一个可以增删改查的后台。 先建一个超级用户： 

python manage.py createsuperuser
# 然后访问 http://127.0.0.1:8000/admin/

最简单的注册只要一行 admin.site.register(Post)。但用 ModelAdmin 可以定制得非常舒服：

from django.contrib import admin

from .models import Post


@admin.register(Post)
class PostAdmin(admin.ModelAdmin):
    list_display = ['title', 'slug', 'author', 'publish', 'status']
    list_filter = ['status', 'created', 'publish', 'author']
    search_fields = ['title', 'body']
    prepopulated_fields = {'slug': ('title',)}
    raw_id_fields = ['author']
    date_hierarchy = 'publish'
    ordering = ['status', 'publish']
    show_facets = admin.ShowFacets.ALWAYS      # Django 5.0：过滤器显示计数
选项效果
list_display列表页显示哪些列
list_filter右侧过滤栏（外键过滤器在有 2 个以上对象时才出现）
search_fields出现搜索框，按这些字段搜索
prepopulated_fields输入标题时自动生成 slug
raw_id_fields外键用 ID 输入框 + 放大镜代替下拉框（用户上千时下拉框会卡死）
date_hierarchy搜索框下方的按年/月/日导航
ordering后台列表的默认排序（覆盖模型的 Meta.ordering）
show_facets在过滤选项旁显示匹配数量，如 “Published (3)”
💡 后台是给“内部人员”用的

Admin 适合编辑、运营、管理员管理数据。不要把它当成面向普通用户的界面来改造 —— 那样会越改越痛苦。 这也是 Two Scoops of Django 反复强调的一点。

ORM 与 QuerySet

ORM（对象关系映射）让你用 Python 对象的方式操作数据库，不必手写 SQL。 它支持 PostgreSQL、MySQL、MariaDB、SQLite、Oracle。核心概念是 QuerySet： 一个“待执行的查询”，相当于一条 SELECT，可以不断叠加过滤条件。

增、改、删

>>> from django.contrib.auth.models import User
>>> from blog.models import Post
>>> user = User.objects.get(username='admin')

# 创建：先建对象再 save()（INSERT）
>>> post = Post(title='Another post', slug='another-post', body='Post body.', author=user)
>>> post.save()

# 一步到位
>>> Post.objects.create(title='One more post', slug='one-more-post', body='...', author=user)

# 有就取，没有就建；返回 (对象, 是否新建)
>>> user2, created = User.objects.get_or_create(username='user2')

# 修改：改属性后 save()（UPDATE）—— 不 save() 数据库就不会变
>>> post.title = 'New title'
>>> post.save()

# 删除：CASCADE 的关联对象会一起删
>>> post.delete()

查：get / all / filter / exclude / order_by

Post.objects.get(id=1)                 # 只取一个：0 个抛 DoesNotExist，多个抛 MultipleObjectsReturned
Post.objects.all()                     # 全部
Post.objects.filter(publish__year=2024, author__username='admin')   # 条件之间是 AND
Post.objects.filter(publish__year=2024).exclude(title__startswith='Why')
Post.objects.order_by('-title')        # 负号 = 降序；'?' = 随机
Post.objects.all()[:5]                 # LIMIT 5（不支持负索引）
Post.objects.filter(id__lt=3).count()  # SELECT COUNT(*)
Post.objects.filter(title__startswith='Why').exists()   # 只判断有没有，比 count() 快

字段查找（field lookups）：双下划线语法

写法含义（SQL）
id=1 / id__exact=1= 1
title__iexact='who'不区分大小写的相等
title__contains='Django' / __icontainsLIKE '%Django%'
id__in=[1, 3]IN (1, 3)
id__gt=3 / __gte / __lt / __lte> >= < <=
title__istartswith='who' / __iendswith以…开头 / 结尾
publish__date=date(2024,1,31)取日期部分比较
publish__year=2024 / __month / __day按年 / 月 / 日
author__username='admin'跨关系查找：自动 JOIN

OR 查询：Q 对象

from django.db.models import Q

starts_who = Q(title__istartswith='who')
starts_why = Q(title__istartswith='why')
Post.objects.filter(starts_who | starts_why)   # |=OR  &=AND  ^=XOR  ~=NOT

自定义管理器

每个模型至少有一个管理器，默认叫 objects。自定义管理器有两种方式： 给现有管理器加方法（Post.objects.my_method()），或者改写它返回的初始 QuerySet（Post.published.all()）。 本书用了第二种： 

class PublishedManager(models.Manager):
    def get_queryset(self):
        return super().get_queryset().filter(status=Post.Status.PUBLISHED)

class Post(models.Model):
    # ...
    objects = models.Manager()      # 显式保留默认管理器！
    published = PublishedManager()

Post.published.filter(title__startswith='Who')
⚠ 第一个声明的管理器就是“默认管理器”

如果你只写了 published = PublishedManager() 而没写 objects，那么 objects 会消失， 而且 Admin、dumpdata 等用默认管理器的地方都只能看到已发布文章。所以书里把 objects 放在前面。

视图、URL 与模板

视图：接收请求，返回响应

from django.shortcuts import get_object_or_404, render

from .models import Post


def post_list(request):
    posts = Post.published.all()
    return render(request, 'blog/post/list.html', {'posts': posts})


def post_detail(request, id):
    post = get_object_or_404(Post, id=id, status=Post.Status.PUBLISHED)
    return render(request, 'blog/post/detail.html', {'post': post})
  • 每个视图的第一个参数都是 request（HttpRequest 对象）。
  • render() 把模板和上下文字典渲染成 HttpResponse，并且会带上上下文处理器提供的变量（比如 user）。
  • get_object_or_404() = get() + 找不到时抛 Http404，省去手写 try/except DoesNotExist。

URL：两层配置 + 命名空间

from django.urls import path

from . import views

urlpatterns = [
    path('', views.post_list, name='post_list'),
    path('<int:id>/', views.post_detail, name='post_detail'),

模板：继承与“挖坑填坑”

Django 模板语言有三种语法：

{% tag %}
模板标签：控制逻辑，如 {% for %}、{% if %}、{% block %}、{% url %}
{{ variable }}
模板变量：渲染时替换成值，默认会做 HTML 转义
{{ var|filter }}
过滤器：加工变量，可以串联，如 {{ post.body|truncatewords:30|linebreaks }}
{% load static %}
<!DOCTYPE html>
<html>
<head>
  <title>{% block title %}{% endblock %}</title>
  <link href="{% static "css/blog.css" %}" rel="stylesheet">
</head>
<body>
  <div id="content">
    {% block content %}
    {% endblock %}
  </div>
  <div id="sidebar">
    <h2>My blog</h2>
    <p>This is my blog.</p>
  </div>
</body>

ⓘ 为什么模板路径是 blog/templates/blog/...，blog 写两遍？

APP_DIRS=True 时，Django 会把所有应用的 templates/ 目录合并成一个搜索空间。 如果两个应用都有 templates/list.html，就会互相覆盖。多套一层以应用名命名的目录，相当于给模板加了命名空间。

def add_favourite(request, id):

代码点评：对照 Django 5.2 与 Two Scoops of Django

本书是教学代码，目标是“把概念讲清楚”，所以常常省略生产项目里必须做的事。 每章结尾我会对照 Django 5.2 官方最佳实践和 Two Scoops of Django（下文简称 TSD）的建议逐条点评。 标签含义：做得好 建议改进 有问题 补充知识。

🔍 第 1 章代码点评 Chapter01/mysite

做得好 用 settings.AUTH_USER_MODEL 引用用户模型

外键写 settings.AUTH_USER_MODEL 而不是 from django.contrib.auth.models import User，以后换成自定义用户模型也不用改这里。TSD 的写法完全一致。

做得好 枚举类 choices、显式索引、应用命名空间

TextChoices 让“魔法字符串”只出现一次；Meta.indexes 为高频排序字段建索引；URL 用 app_name 命名空间、模板用 {% url %} 反向解析。这三个都是值得从第一天就养成的习惯。

有问题 add_favourite 没有登录校验，而且用 GET 修改数据 Chapter01/mysite/blog/views.py:40

① 视图没有 @login_required：匿名用户访问时 request.user 是 AnonymousUser， get_or_create(user=request.user) 会直接抛异常（500 错误）。 ② “收藏”是修改数据的操作，却通过一个普通 <a href> 链接（GET）触发。 GET 请求不受 CSRF 保护，别的网站放一张 <img src="…/favrourite/add/10/"> 就能让已登录用户在不知情时“收藏”； 浏览器预加载、爬虫也可能触发它。HTTP 规定 GET 应当是安全、幂等的。

原代码
def add_favourite(request, id):
    post = get_object_or_404(Post, id=id)
    FavouritePost.objects.get_or_create(
        user=request.user, post=post
    )
    return HttpResponseRedirect(post.get_absolute_url())
建议
@login_required
@require_POST
def add_favourite(request, post_id):
    post = get_object_or_404(Post.published, pk=post_id)
    FavouritePost.objects.get_or_create(
        user=request.user, post=post
    )
    return redirect(post)   # redirect 会调用 get_absolute_url

模板里对应改成一个带 {% csrf_token %} 的小表单按钮。另外 URL 里的 favrourite 是拼写错误（Chapter01/mysite/blog/urls.py:11），并且原代码允许收藏草稿文章（用的是 Post 而不是 Post.published）。

建议改进 查询可以更简洁、更少 SQL

post_detail 用 try/except DoesNotExist 只为判断“是否收藏过”，favourites 用 id__in + 子查询。都可以用更直接的写法：

# 是否收藏：只需要 True/False，用 exists()
is_favourite = (
    request.user.is_authenticated
    and FavouritePost.objects.filter(user=request.user, post=post).exists()
)

# 我的收藏：沿反向关系直接过滤（关系名默认是模型名小写 favouritepost）
favourite_posts = Post.published.filter(favouritepost__user=request.user)

补充知识 复合主键在 5.2 中的限制

CompositePrimaryKey 是 5.2 新增的，生态还在跟进：其他模型不能用 ForeignKey 指向一个复合主键模型； Admin 等组件对它的支持也有限。对“纯关系表”（收藏、点赞、关注）它很合适； 如果以后可能被别的表引用，TSD 的一贯建议仍然是“普通自增主键 + UniqueConstraint”： 

class FavouritePost(models.Model):
    user = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE)
    post = models.ForeignKey(Post, on_delete=models.CASCADE)
    created = models.DateTimeField(auto_now_add=True)

    class Meta:
        constraints = [
            models.UniqueConstraint(fields=['user', 'post'], name='unique_favourite'),
        ]

建议改进 用“QuerySet 方法”代替只改 get_queryset 的管理器 TSD：Fat models / 管理器

Post.published.all() 能用，但不能组合：想要“某作者已发布的文章”只能写 Post.published.filter(author=…)， 想在关系上用（user.blog_posts.published()）就做不到。把过滤逻辑写在自定义 QuerySet 上，再用 as_manager() 生成管理器，任何地方都能链式调用： 

class PostQuerySet(models.QuerySet):
    def published(self):
        return self.filter(status=Post.Status.PUBLISHED)

    def by_author(self, user):
        return self.filter(author=user)


class Post(models.Model):
    # ...
    objects = PostQuerySet.as_manager()

# 用法：可以任意组合，也能用在反向关系上
Post.objects.published().by_author(user)
user.blog_posts.published()

建议改进 抽出 TimeStampedModel 抽象基类 TSD：模型继承

created/updated 这对字段后面的 Comment、Image、Order、Course 等几乎每个模型都会再写一遍。 TSD 推荐做一个抽象基类（不建表，只复用字段）放在公共应用里： 

# core/models.py
class TimeStampedModel(models.Model):
    created = models.DateTimeField(auto_now_add=True)
    updated = models.DateTimeField(auto_now=True)

    class Meta:
        abstract = True


class Post(TimeStampedModel):
    ...

有问题 SECRET_KEY 写死、DEBUG=True Chapter01/mysite/mysite/settings.py:24 TSD：设置与环境变量

这是 startproject 生成的默认值，开发时无所谓，但它一旦进了 Git 就等于公开了。 TSD 的核心原则：密钥不进版本库，配置随环境变化。第 2 章仓库代码开始用 python-decouple 读环境变量， 第 17 章会拆分 settings/ 为 base / local / prod。建议从一开始就这样做： 

SECRET_KEY = config('SECRET_KEY')
DEBUG = config('DEBUG', default=False, cast=bool)     # 默认安全：没配置就是 False
ALLOWED_HOSTS = config('ALLOWED_HOSTS', default='', cast=Csv())

建议改进 删除作者会级联删掉所有文章

on_delete=CASCADE 在教学里最省事，但对内容型网站，“删一个账号就丢一堆文章”通常不是想要的。 可以考虑 PROTECT（先转移文章才能删用户）或 SET_NULL（保留文章，作者置空）， 或者干脆不删用户，只把 is_active 设为 False。

建议改进 tests.py 是空的 TSD：测试

TSD 的原话大意是“没有测试的代码就是坏掉的代码”。至少为模型方法和视图写几个冒烟测试。Django 自带的 TestCase 就够用， TSD 推荐进一步用 pytest-django + factory_boy： 

from django.contrib.auth import get_user_model
from django.test import TestCase
from django.urls import reverse

from .models import Post


class PostViewsTests(TestCase):
    @classmethod
    def setUpTestData(cls):
        user = get_user_model().objects.create_user('alice', password='x')
        cls.draft = Post.objects.create(title='Draft', slug='draft', body='…', author=user)
        cls.live = Post.objects.create(title='Live', slug='live', body='…', author=user,
                                       status=Post.Status.PUBLISHED)

    def test_list_only_shows_published(self):
        resp = self.client.get(reverse('blog:post_list'))
        self.assertContains(resp, 'Live')
        self.assertNotContains(resp, 'Draft')

    def test_draft_detail_is_404(self):
        resp = self.client.get(self.draft.get_absolute_url())
        self.assertEqual(resp.status_code, 404)

补充知识 参数名 id 遮蔽了 Python 内置函数

视图参数叫 id 会遮蔽内置的 id()。更常见的写法是 <int:pk> 或 <int:post_id>，第 2 章的 post_share(request, post_id) 就改成了这种风格。另外查询时写 pk= 比 id= 更通用（主键不一定叫 id）。

小结

  • Django 用 MTV 分工：模型管数据、模板管外观、视图管逻辑，URL 配置负责派发。
  • 项目是配置的集合，应用是可复用的功能模块；新应用要加进 INSTALLED_APPS。
  • 模型字段对应表的列；Meta 里定义排序和索引；用 TextChoices 定义选项；外键用 settings.AUTH_USER_MODEL。
  • 改模型后 makemigrations + migrate；迁移文件要提交到版本库。
  • QuerySet 是惰性的；filter 用双下划线查找，Q 对象实现 OR；自定义管理器封装常用过滤。
  • URL 用命名空间 + 名字反向解析，模板用继承复用骨架。
