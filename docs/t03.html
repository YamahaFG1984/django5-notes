调试与日志：出了错怎么办

初学者最常卡住的地方，往往不是“不会写”，而是“报错了看不懂”。这一篇先教你读懂 Django 的报错页，把最常见的十几种错误整理成速查表， 再介绍 breakpoint()、shell、Debug Toolbar 这几件调试工具。最后讲日志：上线之后没有黄色报错页可看，你只能靠日志和错误监控知道哪里坏了。

本篇目标

  • 按“复现 → 读错误 → 定位 → 验证 → 写测试 → 修复”的顺序处理 bug
  • 读懂 Django 报错页和 traceback，快速找到“你自己的那一行”
  • 认识十几种最常见的 Django 错误和它们的典型原因
  • 用 breakpoint() 暂停程序、查看变量；用 shell 和 Debug Toolbar 查看 SQL
  • 理解 logger、handler、formatter 和日志级别，写出开发与生产两套 LOGGING
  • 用 Sentry 或 ADMINS 邮件接收线上错误，并避免在日志里泄露敏感信息

调试的基本流程

读懂 Django 的报错页

DEBUG = True 时，未处理的异常会显示一个黄色的报错页。以第 4 章点评里的问题为例：一个没有 Profile 的用户打开“编辑资料”页：

💡 三个读错误的习惯
  • 把最后一行读完整。“User has no profile.”已经说明了原因：request.user.profile 这个一对一对象不存在。
  • 找“你的”帧。错误通常在框架内部抛出，但原因在调用它的你的代码里。
  • 搜索时去掉你特有的部分。搜 “RelatedObjectDoesNotExist has no” 而不是带着你的模型名和路径。
⚠ 这个页面只能在开发环境出现

报错页会展示源码、局部变量、请求头和（部分打码的）设置。Django 会把名字里含 API、KEY、PASS、SECRET、SIGNATURE、TOKEN 的设置替换成星号，但你的变量里的其他敏感数据不会。线上必须 DEBUG = False。

常见错误速查

错误典型原因怎么处理书中
ModuleNotFoundError: No module named 'django'虚拟环境没激活，或依赖没装激活 .venv，或用 uv run—

OperationalError: no such table（PostgreSQL 上是 ProgrammingError: relation … does not exist）忘了 makemigrations 或 migrate运行迁移；showmigrations 查看状态1
DisallowedHost（生产环境里是 400）访问的域名不在 ALLOWED_HOSTS把域名加进设置17
403 CSRF verification failed表单缺 {% csrf_token %}；fetch 请求没带 X-CSRFToken 头补上令牌；不要用 @csrf_exempt 绕过6 · 13
Page not found (404)，页面列出“Django tried these URL patterns”URL 拼错、include 前缀不对、少了末尾斜杠对照页面列出的模式逐个检查1
NoReverseMatch{% url %} / reverse() 的名字、命名空间或参数个数不对核对 app_name、name= 和参数1
TemplateDoesNotExist模板路径写错、应用没加进 INSTALLED_APPS看报错页的 “Template-loader postmortem”，它列出了找过的每个位置1
TemplateSyntaxError: Invalid block tag用自定义标签前忘了 {% load %}在模板顶部加 {% load blog_tags %}3
DoesNotExist / MultipleObjectsReturned.get() 查不到或查到多条视图里用 get_object_or_404；可能多条时用 filter().first()14
RelatedObjectDoesNotExist: User has no profile.一对一关联对象没有创建创建用户时一并创建，或用 get_or_create4
FieldError: Cannot resolve keyword查询里的字段名或双下划线路径拼错对照模型字段和 related_name—
IntegrityError: UNIQUE constraint failed违反唯一约束，例如中文标题生成了空 slug保存前校验；表单里捕获并提示6
SynchronousOnlyOperation在 async def 里调用了同步 ORM用 aget() / acreate()，或 sync_to_async16
ⓘ 模板里的“静默错误”

模板变量写错（{{ post.titel }}）不会报错，只会输出空字符串，这是最难发现的一类问题。 调试时可以在 TEMPLATES['OPTIONS'] 里临时设置 'string_if_invalid': 'INVALID(%s)'，写错的变量就会显示出来。用完记得删掉，它不适合一直开着。

breakpoint()：让程序停下来

比起到处 print()，更好的办法是让程序停在某一行，然后交互式地查看任何变量、执行任何表达式。Python 内置的 breakpoint() 就能做到：

@require_POST
def cart_add(request, product_id):
    cart = Cart(request)
    product = get_object_or_404(Product, id=product_id)
    form = CartAddProductForm(request.POST)
    breakpoint()                      # 程序运行到这里暂停，runserver 的终端进入 (Pdb) 提示符
    if form.is_valid():
        ...

命令作用命令作用
n执行下一行（不进入函数）p 表达式 / pp打印 / 美化打印
s进入函数内部l / ll显示附近代码 / 整个函数
c继续运行，直到下一个断点w显示调用栈
r运行到当前函数返回u / d在调用栈里上移 / 下移一层
b 文件:行号再设一个断点q退出（请求会以异常结束）
💡 几个实用技巧
  • PYTHONBREAKPOINT=0 python manage.py runserver 会让所有 breakpoint() 失效；装了 ipdb 后用 PYTHONBREAKPOINT=ipdb.set_trace 可以得到带补全和高亮的调试器。
  • Django 跑在 Docker Compose 里时（第 17 章），给服务加上 stdin_open: true 和 tty: true，再 docker attach 容器名 就能进入 Pdb；按 Ctrl-P Ctrl-Q 脱离而不停止容器。
  • 测试失败时运行 pytest --pdb，会直接停在失败的那一行。
  • 提交前删掉所有 breakpoint()。ruff 的 T100 规则可以帮你检查。

日志：程序自己写的日记

断点只在你坐在电脑前时有用。程序在服务器上运行时，你需要它自己记下发生了什么。Python 的 logging 模块由三类角色组成：

在代码里记日志

以第 9 章的 Webhook 为例。原来的代码在签名错误、订单不存在时直接返回 400 / 404，什么都没留下；Stripe 后台显示投递失败，你却无从查起。

import logging

logger = logging.getLogger(__name__)          # 名字就是 'payment.webhooks'


@csrf_exempt
def stripe_webhook(request):
    payload = request.body
    sig_header = request.META.get('HTTP_STRIPE_SIGNATURE', '')
    try:
        event = stripe.Webhook.construct_event(
            payload, sig_header, settings.STRIPE_WEBHOOK_SECRET
        )
    except ValueError:
        logger.warning('Stripe webhook: invalid payload')
        return HttpResponse(status=400)
    except stripe.error.SignatureVerificationError:
        logger.warning('Stripe webhook: bad signature from %s', request.META.get('REMOTE_ADDR'))
        return HttpResponse(status=400)

    if event.type == 'checkout.session.completed':
        session = event.data.object
        if session.mode == 'payment' and session.payment_status == 'paid':
            try:
                order = Order.objects.get(id=session.client_reference_id)
            except Order.DoesNotExist:
                logger.error('Stripe webhook: order %s not found (event %s)',
                             session.client_reference_id, event.id)
                return HttpResponse(status=404)
            # ...
            logger.info('Order %s paid (payment_intent=%s)', order.id, session.payment_intent)
    return HttpResponse(status=200)

try:
    session = stripe.checkout.Session.create(**session_data)
except stripe.error.StripeError:
    logger.exception('Failed to create Stripe session for order %s', order.id)   # 自动附带完整 traceback
    messages.error(request, 'Payment service is temporarily unavailable. Please try again.')
    return redirect('payment:process')
要这样做原因
logger = logging.getLogger(__name__)，每个模块一个日志里能看到来自哪个模块，也能按模块单独调级别
logger.info('Order %s paid', order.id)，不要写成 f-string级别不够时不会做字符串拼接；Sentry 等工具按“模板”把同类消息归为一组
在 except 块里用 logger.exception(...)等于 ERROR 级别再附上完整 traceback
记录 ID（订单号、事件 ID、用户 ID），不记密码、令牌、完整卡号、邮件正文能排查问题，又不把日志变成泄露源
程序里不用 print()；命令行脚本和管理命令里的输出另说print 没有级别、没有时间、没法关掉。管理命令用 self.stdout.write（第 17 章就是这么做的）
Celery 任务里用 celery.utils.log.get_task_logger(__name__)日志会带上任务名和任务 ID

配置 LOGGING

不写 LOGGING 时，Django 有一套默认配置：DEBUG=True 时 django 的日志输出到控制台，DEBUG=False 时 django.request 的错误发邮件给 ADMINS。你自己模块的 INFO 日志默认哪里都不会显示，所以需要自己配置：

LOGGING = {
    'version': 1,
    'disable_existing_loggers': False,           # 保留 Django 自带的 logger
    'formatters': {
        'simple': {'format': '{levelname} {name}: {message}', 'style': '{'},
    },
    'handlers': {
        'console': {'class': 'logging.StreamHandler', 'formatter': 'simple'},
    },
    'root': {'handlers': ['console'], 'level': 'DEBUG'},
    'loggers': {
        'django': {'handlers': ['console'], 'level': 'INFO', 'propagate': False},
        # 想看每条 SQL 时取消注释（只在 DEBUG=True 时有输出）
        # 'django.db.backends': {'handlers': ['console'], 'level': 'DEBUG', 'propagate': False},
    },
}

LOGGING = {
    'version': 1,
    'disable_existing_loggers': False,
    'formatters': {
        'verbose': {'format': '{asctime} {levelname} {name} {process:d} {message}', 'style': '{'},
    },
    'filters': {
        'require_debug_false': {'()': 'django.utils.log.RequireDebugFalse'},
    },
    'handlers': {
        'console': {'class': 'logging.StreamHandler', 'formatter': 'verbose'},   # 容器里输出到 stdout
        'mail_admins': {
            'class': 'django.utils.log.AdminEmailHandler',
            'level': 'ERROR',
            'filters': ['require_debug_false'],
        },
    },
    'root': {'handlers': ['console'], 'level': 'INFO'},
    'loggers': {
        'django': {'handlers': ['console'], 'level': 'WARNING', 'propagate': False},
        'django.request': {'handlers': ['console', 'mail_admins'], 'level': 'ERROR', 'propagate': False},
    },
}

不要让错误报告泄露敏感数据

错误邮件和 Sentry 都会附带请求的 POST 数据和局部变量。第 4 章的注册视图出错时，报告里就会有用户刚输入的明文密码。Django 提供了两个装饰器，把这些值替换成星号：

from django.views.decorators.debug import sensitive_post_parameters, sensitive_variables


@sensitive_post_parameters('password', 'password2')    # 错误报告里隐藏这两个 POST 字段
def register(request):
    ...


@sensitive_variables('card_number')                    # 隐藏这个局部变量
def charge(request):
    card_number = ...

17 章的代码里没有任何 import logging，也没有 LOGGING 设置。支付、Webhook、Celery 任务这些最需要留下记录的地方，失败时只返回一个状态码。至少给 Webhook、支付、邮件任务加上日志（示例见上文）。

小结

  • 先复现、读错误、定位到“你的那一行”，再提出假设并验证；修复前先写一个失败的测试。
  • 报错页从上往下读：异常类型和信息 → 触发的视图 → 最后一个属于你的帧 → 局部变量。
  • breakpoint() 让程序停下来交互式检查；shell 和 Debug Toolbar 用来看 SQL。
  • 日志由 logger、handler、formatter 组成；每个模块 getLogger(__name__)，用 % 占位符，异常用 logger.exception。
  • 线上要 DEBUG = False，靠日志平台、Sentry 或 ADMINS 邮件得知错误；用 sensitive_* 装饰器隐藏敏感数据。
